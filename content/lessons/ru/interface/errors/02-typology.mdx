<DropCap>В</DropCap> большинстве дизайн-систем есть один и тот же компонент — `<ErrorMessage>`. Один компонент на все случаи: подсветить поле, объяснить сбой сервера, предупредить о потерянном соединении, попросить заново залогиниться. Снаружи это чистая абстракция; внутри — смешение четырёх разных событий, у которых разная природа, разные сроки реакции, разные обязательства команды и разные маршруты восстановления. Универсальная формулировка звучит вяло во всех четырёх случаях.

Эта тема — о том, как разнести «ошибки» на четыре типа и привязать к каждому свою механику: где её показывать, как формулировать, какие ARIA-атрибуты ставить, какие действия предлагать. Предыдущая тема (`interface/errors/01-patterns`) разделяла ошибки по recoverability и по HTTP-семантике на уровне экрана; тема валидации форм (`interface/forms/02-validation`) разбирала тайминг inline-сообщений. Здесь мы соединяем оба разговора в одну рабочую таксономию: validation, network, server, forbidden — четыре класса, у каждого свой паттерн.

<SectionBreak id="01" label="ЧЕТЫРЕ ТИПА ОШИБОК — НЕ ОДИН" />

Don Norman в «The Design of Everyday Things» (издано в 1988 году как *The Psychology of Everyday Things*, переименовано в DOET в 1990-м) сформулировал тезис, до сих пор работающий фильтром при ревью любого error-флоу: ошибки — нормальная часть использования, а не девиация. Задача дизайна — сделать выход из ошибки тривиальным. Из этого тезиса вытекает практический вопрос: какая *именно* ошибка случилась и кто отвечает за выход.

Удобная классификация группирует ошибки по двум осям — *кто причина* и *кто действует*. Получаются четыре класса.

**Validation** — данные, введённые пользователем, не прошли проверку. Причина и действие — на пользователе (опечатка, неполное поле, неверный формат; исправить и попробовать снова). Сервер при этом здоров. В этой клетке живут классические inline-сообщения «email должен содержать @» и «пароль не может быть пустым».

**Network** — запрос не дошёл или не вернулся. Причина — между клиентом и сервером (Wi-Fi отвалился, мобильная сеть слабая, captive portal, DNS не разрешается). Действие — частично на пользователе (подождать, переключить сеть), частично на клиенте (автоматический retry, queue невыполненных запросов).

**Server** — запрос дошёл, но сервер не смог ответить. 500, 502, 503, 504 по таксономии RFC 9110 (HTTP Semantics, 2022). Причина — на стороне команды; пользователь не виноват. Действие в момент инцидента — на разработчиках; пользователь может только повторить запрос.

**Forbidden** — пользователь не имеет права на запрошенное действие или ресурс. 401 (нет валидной сессии), 403 (нет прав), 410 (ресурс удалён), expired session внутри длинного flow. Действие — re-authentication, эскалация к admin или принятие факта, что доступа не будет.

У каждого класса свои тайминги показа, свой surface (inline / banner / modal / toast), своя структура текста, свои ARIA-атрибуты. Универсальный компонент вынуждает делать компромисс на каждый класс; чёткая таксономия даёт один компонент с разными вариантами — каждое сообщение попадает в свою клетку без компромисса.

<MarginNote>
Don Norman, *The Design of Everyday Things* — переиздание 1990 года под новым названием (изначально вышло как *The Psychology of Everyday Things*, 1988); расширенное Revised and Expanded Edition вышло в 2013-м. Глава «To Err Is Human» формулирует разделение slips (моторные оплошности) и mistakes (ошибки в модели задачи) — оно не сводится к нашей четвёрке, но даёт основу для разговора о том, что разные ошибки требуют разных интерфейсов.
</MarginNote>

<SectionBreak id="02" label="VALIDATION: INLINE, IMMEDIATE, SPECIFIC" />

Validation — самый частый класс ошибок в продуктах с формами. Тема `interface/forms/02-validation` разобрала тайминг: on-blur после первой валидации, real-time при исправлении. Здесь нас интересует другой срез — что делать, когда часть проверок невозможна на клиенте.

Клиент знает синтаксис, но не знает мира. Он умеет проверить, что в email-поле есть `@`, что пароль не короче восьми символов, что номер приведён к E.164. Чего клиент не знает: занят ли логин (знает база), валиден ли купон (знает биллинг), существует ли домен (знает MX-сервер). Эти проверки делает сервер, и их результат приходит асинхронно — через сотни миллисекунд после submit.

Стандартная ошибка — отдавать server-side validation на отдельном surface: одни проверки inline под полем, другие — модальным окном посередине экрана. Контекст ломается: пользователь смотрит на форму, ищет проблему рядом с полем, и не находит. Решение: server-side validation должна возвращаться на тот же inline-spot, что и client-side. Бэкенд отдаёт структурированный ответ — `{ field: "email", message: "Адрес уже зарегистрирован — войти?" }`; клиент рендерит его под нужным полем с теми же ARIA-атрибутами. Пользователь не видит разницы в природе проверки.

Структура сообщения — *what / why / what to do*. Формат, формализованный в heuristic #9 Jakob Nielsen из *10 Usability Heuristics* (1994, обновлено в 2020), «Help users recognize, diagnose, and recover from errors», работает в любом из четырёх классов. У validation он короткий — у пользователя в фокусе одно поле:

```text
Bad:  Invalid input.
Good: Адрес должен содержать символ @ и домен — например, name@company.ru.
```

Первое сообщение нарушает все три части. Второе закрывает их за одну строку: что не так — нет `@` или домена; почему — это требование к формату; что делать — добавить недостающие части плюс конкретный пример.

ARIA для inline-валидации построена вокруг двух атрибутов. `aria-invalid="true"` на самом поле сообщает screen reader, что значение некорректное. `aria-describedby` связывает поле с текстовым сообщением — ридер озвучивает описание сразу после имени и типа поля.

```html
<label for="email">Email</label>
<input
  id="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
  required
/>
<p id="email-error" role="alert">
  Адрес должен содержать символ @ и домен — например, name@company.ru.
</p>
```

`role="alert"` на сообщении делает его assertive live region — ридер прерывает текущую речь. Это уместно для ошибки, появившейся в ответ на действие пользователя. Если сообщение существовало на странице с открытия (форма с сохранёнными невалидными значениями), `role="alert"` избыточен — ридер озвучит его при попадании фокусом через `aria-describedby`.

<MarginNote>
WAI-ARIA 1.0 (W3C Recommendation, 20 марта 2014 года) формализовала `role="alert"`, `role="status"`, `aria-live`, `aria-invalid` и связанные атрибуты. До ARIA доступная динамическая ошибка в HTML требовала JavaScript-хаков с фокус-менеджментом; ARIA дала декларативный язык, который понимают все современные screen reader.
</MarginNote>

<SectionBreak id="03" label="NETWORK: RETRY, QUEUE, OFFLINE MODE" />

Network-ошибки отличаются от validation тем, что причина — не в данных, а в канале. Запрос корректен, сервер готов ответить, но между ними нет связи. Большая часть работы — на стороне клиента, который должен спрятать временные сбои и нагнать состояние, когда сеть вернётся.

Стандартный паттерн — три уровня реакции, разнесённые по времени.

**Silent retry.** Один автоматический повтор через одну-две секунды без UI. Большинство сетевых сбоев — микрозапинки на десятки миллисекунд: пакет потерялся, мобильная сеть переключилась с одной соты на другую. За две секунды повтор обычно проходит, пользователь ничего не заметит.

**Пользовательский баннер.** Если retry не прошёл, появляется баннер сверху или снизу viewport: «Нет подключения, повторяем». Без блокировки UI — пользователь читает загруженное, листает кэшированные экраны. Текст честный, без эвфемизмов.

**Queue и обещание.** Если сеть не вернулась, запрос сохраняется локально и отправляется автоматически при возврате подключения. «Ваши изменения сохранятся и отправятся, когда подключение восстановится» — обещание, выполнимое только если queue реально реализован (Service Worker, IndexedDB, background sync). Без реализации обещание превращается в обман.

Service Worker API получил стабильную поддержку в Chrome 40 (январь 2015), Firefox 44 (январь 2016) и Safari 11.1 (март 2018). Спецификация позволяет перехватывать failed fetch-запросы на уровне браузера, кэшировать их и переотправлять при возврате сети. Архитектурно queue — отдельная тема (`experience/flows/03-error-recovery`); для типологии важно одно: network — единственный класс, в котором клиент берёт значительную часть восстановления на себя.

Различимость трёх состояний — отдельная подзадача. «Нет интернета» (Wi-Fi выключен), «timeout» (соединение есть, но запрос не дошёл) и «server unreachable» (DNS не разрешается) — три разных события. Грамотный клиент различает их хотя бы поверхностно: если `navigator.onLine === false`, показываем «нет подключения»; таймаут — «связь нестабильна»; network error при онлайн-флаге — «сервер недоступен».

ARIA для network-баннера — `role="status"` или `aria-live="polite"`. В отличие от validation, где `role="alert"` уместен, network-баннер не требует прерывания: ридер должен сообщить о нём в ближайшую паузу.

```html
<div role="status" aria-live="polite" class="network-banner">
  Нет подключения. Повторяем попытку.
</div>
```

<MarginNote>
Спецификация Service Worker API доступна на developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API. Канонические рецепты — Cache First, Network First, Stale-While-Revalidate — описаны там же. Для background sync существует отдельный API, поддерживаемый в Chrome и Edge с 2016 года; в Firefox и Safari альтернативы реализуются через IndexedDB plus периодический повтор.
</MarginNote>

<SectionBreak id="04" label="SERVER: 500, 503, 502 — ЧТО ПОКАЗЫВАТЬ" />

Server-ошибки — самый враждебный класс для пользователя. У validation он понимает, что не так с данными; у network видит, что нет соединения; у forbidden понимает, что нет прав. У server-ошибки он видит, что что-то сломалось, но не понимает что и сделать ничего не может. Хороший дизайн минимизирует это бессилие — даёт минимум информации для retry и максимум честности, что виновата команда.

RFC 9110 (HTTP Semantics, 2022) фиксирует 5xx-коды. 500 — общий «что-то сломалось внутри». 502 — proxy получил некорректный ответ от upstream. 503 — сервис временно недоступен. 504 — upstream не ответил вовремя. Для пользователя все четыре переводятся одинаково — «сервер не смог».

Стандартная структура экрана — три элемента. **Reassurance** — короткое признание, что команда в курсе. «Не удалось загрузить страницу — мы уже разбираемся» лучше, чем «Произошла ошибка»: первое признаёт проблему, второе — пассивная конструкция, скрывающая ответственность. **Retry affordance** — кнопка попробовать ещё раз; большинство 5xx — короткие инциденты, retry часто срабатывает. **Error ID для саппорта** — короткий идентификатор вроде `err_2cf8a1b9`, по которому support попадает в нужную запись логов. Не stack trace, не HTTP-код.

```text
Bad:  Internal Server Error 500. Stack trace: TypeError at line 42...
Good: Не удалось загрузить страницу — мы уже разбираемся.
      Попробуйте обновить через минуту.
      Если ошибка повторится, сообщите код err_2cf8a1b9.
      [Попробовать снова]
```

Жаргон, HTTP-коды и stack traces в визуальном тексте — антипаттерн. Hoa Loranger (NN/g) в статье «Plain Language Is for Everyone, Even Experts» (8 октября 2017) показала, что pseudo-friendly copy и технический жаргон одинаково снижают воспринимаемую competence бренда, причём даже у экспертной аудитории. Plain language — краткое, конкретное, без эвфемизмов и терминологии — выигрывает на любых пользователях.

Stack traces, raw error messages, JSON-payload'ы должны идти в *другой* канал — в Sentry, Datadog, собственный logger. Sentry (David Cramer, основан в 2008 году) формализовал индустриальный стандарт: ошибка с полным контекстом летит в backend; пользователь видит plain-language сообщение и error_id для связи.

ARIA для server-ошибки на полноэкранном экране почти не нужна — экран сменился, фокус попадает на новый контент. Если ошибка показывается баннером поверх существующего экрана (save не прошёл, форма осталась), `role="alert"` обязателен — иначе пользователь, переместивший фокус дальше, не узнает о провале.

```html
<div role="alert" class="form-error">
  Не удалось сохранить — временная проблема на сервере.
  Попробуйте через минуту. Ваши данные не потеряны.
  <button type="button">Сохранить ещё раз</button>
</div>
```

«Ваши данные не потеряны» — отдельная важная строка для server-ошибок на формах. Пользователь в первую очередь боится потерять введённое; прямое подтверждение снимает тревогу и удерживает от закрытия вкладки.

<MarginNote>
Apple Human Interface Guidelines в разделе Alerts формулируют формат error message как «короткое сообщение в title, объяснение в body, действия в кнопках». Title — что произошло (без HTTP-кодов и жаргона), body — почему и что делать, кнопки — конкретные действия, начинающиеся с глагола. HIG также предписывает избегать восклицательных знаков и слов «error», «warning» в визуальном тексте — структура и иконка уже передают severity.
</MarginNote>

<SectionBreak id="05" label="FORBIDDEN: 401, 403, 410, EXPIRED SESSION" />

Forbidden — особый класс. Ошибка не в данных, не в канале, не в сервере — в правах. Структура сообщения и стратегия retry здесь принципиально иные.

**401 Unauthorized.** Сервер не видит валидной сессии или токена. Аккаунт у пользователя есть, просто запрос не авторизован — сессия истекла, токен испортился, cookies стёрлись. Стандартный паттерн — *silent re-login*: redirect на страницу входа, после логина — обратный редирект на исходный URL с восстановлением state. Пользователь воспринимает это как одно событие «попросили залогиниться, продолжил работу», а не как две задачи. Текст на странице логина отличается от обычного входа: «Сессия истекла, войдите снова, чтобы продолжить».

**403 Forbidden.** Сервер видит валидную сессию, но у пользователя нет прав на действие. Это *authorization*, не *authentication*. Стандартный паттерн — *explanatory message + suggest alternative*. «У вас нет прав на удаление этой страницы. Обратитесь к администратору workspace или попросите расширить роль» — объяснение, кто может помочь. Без alternative пользователь упирается в стену.

```text
Bad:  403 Forbidden.
Good: У вас нет прав на удаление этой страницы.
      Обратитесь к администратору workspace или попросите
      расширить роль до Editor.
      [Связаться с администратором]
```

**410 Gone.** Ресурс был, но удалён; команда знает, что он был (в отличие от 404, где сервер не знает). 410 — частный случай fatal-ошибки: retry не поможет. Паттерн — *explain + offer to navigate back*. «Эта страница была удалена 12 марта 2026 года. Перейти к списку проектов или связаться с владельцем».

**Expired session внутри длинного flow** — самый дорогой случай. Пользователь полчаса заполнял checkout-форму; сессия по таймеру истекла, submit падает с 401. Прямой redirect на логин с обнулением state — катастрофа: десять минут работы потеряны, пользователь закрывает вкладку. Правильный паттерн — *Recovery State*: state сохраняется в localStorage или server-side draft; при истечении сессии показывается inline-сообщение «Сессия истекла, войдите снова, чтобы завершить заказ»; после логина пользователь возвращается с восстановленными значениями полей. Подробно паттерны recovery разобраны в `experience/flows/03-error-recovery`.

Различие между 401 и 403 — типичная путаница. 401 означает «мы не знаем, кто ты — авторизуйся»; 403 — «мы знаем, кто ты, и тебе нельзя». 401 ведёт на логин, 403 объясняет ограничение и предлагает escalation. Перепутывание даёт «войдите ещё раз» при 403; пользователь логинится, попадает обратно на тот же экран и не понимает, почему его отказывают признавать.

<MarginNote>
RFC 9110 (HTTP Semantics, июнь 2022) консолидировала ранее разнесённые по нескольким документам определения статус-кодов. 401 в спецификации требует от сервера присылать `WWW-Authenticate` header — на практике в современных продуктах это игнорируется, и 401 используется как общий signal «сессия невалидна». 410 формально SHOULD использоваться, когда условие ожидается постоянным, в отличие от 404, где состояние неизвестно.
</MarginNote>

<SectionBreak id="06" label="SURFACE: INLINE, BANNER, MODAL, TOAST" />

Четыре типа ошибок ложатся на четыре основных surface — inline, banner, modal, toast. Связь не один-к-одному, но базовое распределение устойчивое.

**Inline** — сообщение рядом с компонентом, к которому относится: под полем, рядом с упавшей карточкой, под кнопкой. Не блокирует, не уводит из контекста. Подходит для validation и contextual errors. ARIA — `aria-describedby` на компоненте плюс `role="alert"` или `aria-live="polite"` на тексте.

**Banner** — горизонтальная полоса сверху или снизу viewport, видимая, пока проблема не решена. Подходит для page-level или session-level состояний: offline-режим, maintenance window, системные предупреждения. ARIA — `role="status"` для нейтральных, `role="alert"` для критичных.

**Modal** — блокирующее окно, требующее явного действия. Подходит редко: для expired session с обязательным re-login, для critical confirmation, для блокирующих ошибок. Используется реже остальных, потому что прерывает поток — это всегда дорогая интервенция. Семантика — нативный `<dialog>` с `aria-modal="true"`; фокус-trap внутри, escape-key закрывает (если действие optional), фокус возвращается на исходный элемент.

```html
<dialog aria-modal="true" aria-labelledby="dialog-title">
  <h2 id="dialog-title">Сессия истекла</h2>
  <p>Войдите снова, чтобы продолжить работу. Введённые данные сохранены.</p>
  <button type="button">Войти</button>
</dialog>
```

**Toast** — короткое всплывающее уведомление в углу экрана, исчезающее через 4-6 секунд. Не блокирует, не требует действия. Подходит для transient errors малой важности: autosave failed, undo available, background sync error. ARIA — `aria-live="polite"` или `role="status"`. Не использовать для критичных ошибок — пользователь, отвернувшийся на пять секунд, пропустит сообщение полностью.

WCAG 2.1 Success Criterion 4.1.3 «Status Messages» (Level AA) формализует требование: status-сообщения, появляющиеся без перемещения фокуса, должны быть доступны assistive technology через ARIA live regions. Это покрывает все четыре surface. Без правильной ARIA пользователь screen reader не узнает, что autosave упал, сессия истекла, нет подключения — и продолжит работать, не зная о проблеме.

Краткая сводка:

```text
type        | typical surface  | ARIA pattern
------------|------------------|------------------------------------------
validation  | inline           | aria-invalid + aria-describedby + role="alert"
network     | banner           | role="status" + aria-live="polite"
server      | banner / inline  | role="alert" (если появилось в ответ на submit)
forbidden   | modal / page     | <dialog> + aria-modal="true" для re-login
            |                  | страница с h1 для 403/410
transient   | toast            | aria-live="polite" + role="status"
```

Главное предостережение — не путать roles. `role="alert"` прерывает речь screen reader немедленно; использовать его для toast или нейтрального баннера — значит мучить пользователя ридера прерываниями на сообщения, не требующие реакции. `role="status"` и `aria-live="polite"` — мягкая альтернатива. Граница простая: критичная ошибка, требующая немедленного внимания, — `alert`; информационное сообщение — `status`.

<Exercise title="Audit error states: 12 случаев, 4 типа">
  **Описание.** Knowledge_check: применить таксономию из этой темы к audit-сценарию.

  **Сценарий.** Вам поручают audit error states существующего SaaS-продукта — project management для команд 15-50 человек. Команда нашла 12 разных error message форматов: где-то модалка, где-то toast, где-то inline, где-то полноэкранный экран. Тексты разным голосом: местами с emoji и «упс», местами с HTTP-кодами, местами просто «Error». Вы должны привести зоопарк к 4 типам и описать стандартный pattern для каждого.

  **Задание.** Опишите четыре решения с обоснованием.

  (1) **Классификация 12 случаев в 4 типа.** По 2-3 конкретных примера на класс. Validation — «email уже зарегистрирован», «название проекта не может быть пустым», «дата deadline в прошлом». Network — «не удалось сохранить задачу — нет подключения». Server — «не удалось открыть доску». Forbidden — «у вас нет прав на удаление workspace».

  (2) **Surface для каждого типа.** Validation → inline под полем (проблема видна рядом с полем); network → banner вверху viewport (session-level, не блокирует чтение); server → inline-баннер на форме при сабмите, full-page для page-load failure; forbidden → inline explanatory для 403, modal для expired session с re-login.

  (3) **Text format.** Structure what / why / what to do. Validation — короткое, с примером корректного значения. Network — описание текущего состояния (retry, queue). Server — reassurance + retry + error_id; никаких HTTP-кодов и stack traces. Forbidden — explanation, кто может помочь; для 401 — silent re-login с возвратом, для 403 — suggest alternative.

  (4) **ARIA.** Validation — `aria-invalid="true"` плюс `aria-describedby` плюс `role="alert"`. Network — `role="status"` или `aria-live="polite"`. Server-баннер на форме — `role="alert"`. Forbidden modal — `<dialog>` с `aria-modal="true"` плюс focus-trap. Toast — `aria-live="polite"`.

  **Критерии оценки.** (а) Все 12 случаев распределены без «универсальной» клетки, каждый отнесён к классу по *причине* и *тому, кто действует*. (б) Каждому классу соответствует основной surface с обоснованием «не ломает контекст», «не блокирует чтение»; modal используется минимально. (в) Все сообщения проходят фильтр what / why / what to do; нет HTTP-кодов и stack traces; нет «упс» и emoji; server содержит error_id, validation — пример. (г) Различие между `role="alert"` и `role="status"` / `aria-live="polite"` использовано осознанно; modal использует нативный `<dialog>`, не `<div>`-обёртку; toast не использует `alert`.
