<DropCap>П</DropCap>редыдущие темы рассматривали таблицу как поверхность: типографику, плотность, sticky-колонки, виртуализацию. Эта тема — про взаимодействие с данными внутри неё. Таблица на тысячах строк бесполезна, если пользователь не может изменить порядок строк, сузить набор до релевантного подмножества и перемещаться по результату предсказуемо. Сортировка, фильтрация и пагинация — три механизма, через которые таблица из статичного дампа превращается в инструмент. Все три кажутся тривиальными на мокапе с пятьюдесятью строками и оказываются нетривиальными на проде: где живёт состояние, что уходит на сервер, что остаётся в браузере, как это объявляется screen reader'у и что попадает в URL.

Разберём sort affordances и `aria-sort`, разницу между фильтром и поиском, паттерны фильтрующего UI (inline, global, chips, faceted), четыре стратегии пагинации с их компромиссами, границу между client-side и server-side обработкой, URL как хранилище состояния и accessibility всего перечисленного.

<SectionBreak id="01" label="СОРТИРОВКА: AFFORDANCE И НАПРАВЛЕНИЕ" />

Сортировка меняет порядок строк, не скрывая ни одной. Базовый affordance — кликабельный заголовок колонки: клик переключает порядок, индикатор направления (стрелка ↑/↓) показывает текущее состояние, повторный клик инвертирует. Часто третий клик сбрасывает сортировку к естественному порядку (default sort) — поведение полезное, но не универсальное: одни продукты сбрасывают, другие циклически переключают только между ascending и descending.

Кликабельный элемент внутри `<th>` — это `<button>`, не голый текст с обработчиком клика. Button фокусируется клавиатурой, активируется по Enter и Space, корректно появляется в accessibility tree. Сам `<th>` остаётся семантическим заголовком; интерактивным контролом служит вложенный button. Состояние сортировки объявляется атрибутом `aria-sort` на `<th>` — он появился в WAI-ARIA 1.0 (W3C Recommendation, март 2014) и принимает четыре значения: `ascending`, `descending`, `none`, `other`. Значение `other` означает порядок, который не является ни возрастающим, ни убывающим (например, ручная перестановка); на практике почти всегда используются первые три.

```html
<thead>
  <tr>
    <th scope="col" aria-sort="none">
      <button type="button">SKU</button>
    </th>
    <th scope="col" aria-sort="descending">
      <button type="button">Обновлено</button>
    </th>
    <th scope="col" aria-sort="none">
      <button type="button">Количество</button>
    </th>
  </tr>
</thead>
```

Важная деталь семантики: `aria-sort` ставится только на ту колонку, по которой сейчас идёт сортировка. Если пометить все три заголовка значением `none`, кроме активного, — это корректно; если оставить `aria-sort` на нескольких колонках одновременно при single-column sort, screen reader сообщит противоречивое состояние. Активная колонка несёт `ascending` или `descending`, остальные — `none` либо вовсе не имеют атрибута.

<MarginNote>
`aria-sort` относится к заголовочной ячейке (`<th>` или элементу с `role="columnheader"`), а не к таблице целиком. Визуальная стрелка и значение атрибута должны меняться синхронно: рассинхрон — частый баг, при котором зрячий пользователь видит ↓, а screen reader озвучивает «ascending».
</MarginNote>

<SectionBreak id="02" label="MULTI-SORT, ЕСТЕСТВЕННЫЙ ПОРЯДОК, СТАБИЛЬНОСТЬ" />

Сортировка по нескольким колонкам (multi-column sort) — power-feature. Shift+click по второму заголовку добавляет вторичный ключ: строки сортируются сначала по первому столбцу, при равенстве — по второму. Индикатор должен показывать приоритет: стрелка плюс порядковый номер (1, 2, 3). Большинство пользователей никогда не нажмут Shift, но для аналитических сценариев (сортировка по региону, внутри региона — по выручке) multi-sort необходим. Реализуя его, обязательно показывать активность визуально — иначе таблица перестраивается «магически», и доверие к ней падает.

Естественный порядок (default / natural sort order) — состояние, в котором таблица открывается до любого пользовательского действия. Для журнала транзакций это обычно убывание по дате (свежее сверху); для каталога — алфавит по названию; для очереди задач — приоритет. Естественный порядок выбирается под то, что пользователь ищет в первую секунду после открытия, и должен быть осмысленным, а не «как пришло из базы».

Отдельный технический пункт — стабильность сортировки (stable sort). Стабильный алгоритм сохраняет относительный порядок элементов с равными ключами: если две строки имеют одинаковую дату, после сортировки по дате они останутся в том же взаимном порядке, в каком были до неё. Это и делает работоспособным multi-sort и последовательную ручную сортировку: пользователь сортирует по дате, затем по статусу — и внутри каждого статуса даты остаются упорядоченными, потому что предыдущая сортировка не была разрушена. Спецификация ECMAScript требует, чтобы `Array.prototype.sort` был стабильным начиная с редакции ES2019; современные движки это гарантируют. На сервере стабильность зависит от СУБД и запроса: `ORDER BY` без полностью детерминированного набора ключей не гарантирует устойчивый порядок между запросами, поэтому в ключ сортировки добавляют tie-breaker — уникальный столбец (обычно первичный ключ) последним полем.

<MarginNote>
Нестабильная сортировка проявляется коварно: строки с равными ключами «прыгают» местами при каждой пересортировке или при пагинации, и одна и та же запись может оказаться то на границе страницы 2, то на границе страницы 3. Лечится добавлением уникального tie-breaker в конец ключа сортировки.
</MarginNote>

<SectionBreak id="03" label="ФИЛЬТР ПРОТИВ ПОИСКА" />

Фильтр и поиск часто путают, хотя это разные механизмы. Фильтр (filter) сужает набор по структурированному условию, привязанному к полю: «статус = открыт», «количество < 10», «обновлено за неделю». Условие точное, предсказуемое, обычно перечислимое. Поиск (search) — это текстовый запрос по одному или нескольким полям сразу, часто с нечётким совпадением, ранжированием релевантности и токенизацией. Фильтр отвечает на «покажи всё, что удовлетворяет условию»; поиск — на «найди то, что похоже на это».

Различие практическое, а не терминологическое. Фильтр детерминирован: результат «статус = открыт» одинаков всегда и легко сериализуется в условие. Поиск размыт: «акме» может найти «Acme Corp», «ACME Ltd» и «акмеизм» в примечании, порядок результатов определяется релевантностью. Объединять их в один input — частая ошибка: пользователь вводит точное значение, ожидая фильтр, а получает нечёткий поиск с лишними строками, или наоборот. Корректный паттерн — разделять: global search bar для «найди где-то здесь» и явные фильтры для «именно это поле равно этому значению».

<SectionBreak id="04" label="ФИЛЬТРУЮЩИЙ UI: INLINE, GLOBAL, CHIPS" />

Inline column filter прикреплён к конкретной колонке: иконка-воронка в заголовке, клик раскрывает popover с checkbox-списком значений, диапазоном или input'ом. Паттерн привычен по Excel и хорош для категориальных колонок. Цена — усложнение заголовка: внутри `<th>` появляется второй интерактивный элемент рядом с sort-button, popover требует focus-trap (паттерн модального окна), а ARIA-разметка обрастает `aria-haspopup`, `aria-expanded`, `aria-controls`. На узких колонках label обрезается, оставляя «Кол…» вместо «Количество». Эти издержки разбирались в теме о плотности.

Global filter bar — отдельная панель над таблицей, не встроенная в заголовки. Header остаётся чистым (только сортировка), а фильтры собираются в одном месте сверху. Преимущество — клавиатурная навигация по таблице не ломается, и все активные условия видны разом. Недостаток — фильтры визуально «оторваны» от колонок, и пользователю, привыкшему к Excel-парадигме, требуется привыкание.

Активное состояние фильтрации — обязательный элемент, а не опция. Самый ясный паттерн — filter chips (токены): каждый активный фильтр показан отдельным чипом с возможностью снятия — «Статус: Открыт ×», «Количество < 10 ×», «Поставщик: Acme ×». Рядом — счётчик результата («Показано 47 из 1 250») и кнопка «Сбросить всё». Без видимого состояния пользователь ищет строку, которой нет в выдаче, и теряет время, не понимая, что она отфильтрована.

Faceted filtering (фасетный поиск) — расширение, при котором рядом с каждым возможным значением фильтра показано число строк, которые останутся при его применении: «Открыт (312)», «В работе (88)», «Закрыт (1 401)». Фасеты пересчитываются по текущему набору (с учётом уже применённых других фильтров) и избавляют от тупиковых выборов, ведущих к пустому результату. Паттерн пришёл из e-commerce-каталогов и поисковых интерфейсов; на больших наборах подсчёт фасетов делается на сервере.

Очистка фильтров должна быть симметрична применению: крестик на каждом чипе снимает один фильтр, «Сбросить всё» — все сразу. И отдельный обязательный случай — пустой результат после фильтрации (empty-result state). Это не та же ситуация, что пустая таблица без данных: данные есть, но текущая комбинация фильтров не дала совпадений. Сообщение должно говорить именно это («Ничего не найдено по выбранным фильтрам») и предлагать действие — снять последний фильтр или сбросить все, — а не показывать generic-иллюстрацию «здесь пусто», которая дезориентирует.

<MarginNote>
Empty-result после фильтрации и empty-state пустой таблицы — разные состояния с разными сообщениями. Первое означает «уберите условие»; второе — «добавьте данные». Подмена одного другим — частый источник растерянности: пользователь видит «создайте первую запись», хотя записи есть и лишь отфильтрованы.
</MarginNote>

<SectionBreak id="05" label="ПАГИНАЦИЯ: ЧЕТЫРЕ СТРАТЕГИИ" />

Когда строк больше, чем разумно показать сразу, набор разбивается на части. Существует четыре основных подхода, и выбор между ними определяется сценарием, а не только объёмом данных.

Классическая нумерованная пагинация (numbered pagination) — страницы по 25/50/100 строк, навигация снизу: «Назад», «Вперёд», номера, переход к конкретной странице. Преимущества — deep linking (URL вида `?page=12&size=50` сохраняется, отправляется коллеге, открывается из закладки), точная и воспроизводимая навигация, естественная граница для bulk-действий («выбрать всё» на странице означает 50 строк, не миллион). Стандарт для admin-панелей, выдачи поиска, листингов.

«Load more» (кнопка «Показать ещё») — данные добавляются к уже показанным по явному клику. Сохраняет контроль пользователя (подгрузка происходит по действию, а не автоматически), не ломает футер страницы, проще в реализации, чем infinite scroll. Минус — после многих кликов список становится длинным, а позиция в нём не отражается в URL.

Infinite scroll (бесконечная прокрутка) — следующий чанк подгружается автоматически при приближении к концу. Канон feed-интерфейсов. Преимущество — непрерывность сканирования без когнитивной нагрузки от навигации. Минусы серьёзны: невозможность вернуться к конкретной позиции без прокрутки с начала, URL не отражает положение, deep linking не работает, и — отдельный конфликт — недостижимый футер: если внизу страницы есть значимые элементы (ссылки, контакты, настройки), они отодвигаются при каждой подгрузке, и пользователь до них не доходит. Поэтому infinite scroll уместен для read-only лент и почти всегда вреден в admin-интерфейсах и на страницах с футером.

Cursor-based pagination (курсорная) — это не UI-паттерн, а способ запроса данных, который может стоять под любым из предыдущих. Вместо «пропусти 10 000, верни следующие 50» сервер получает курсор — указатель на последний виденный элемент («верни 50 строк после записи с id=X и датой=Y»). Подробнее о её механике — в следующей секции; на уровне UI она обычно сочетается с «load more» или infinite scroll.

Выбор page-size — отдельное решение. Селектор размера страницы (25 / 50 / 100) даёт пользователю контроль над компромиссом «строк на экране vs частота навигации»; выбор стоит сохранять в пользовательских настройках, как и плотность. И вопрос, который задают слишком поздно: нужна ли пагинация вообще. Для набора в несколько сотен строк виртуализация с непрерывным скроллом нередко удобнее любой пагинации; пагинация оправдана, когда нужен deep linking к странице, когда данные дороги в передаче или когда серверу выгоднее отдавать порциями.

<SectionBreak id="06" label="OFFSET ПРОТИВ CURSOR: ПРОИЗВОДИТЕЛЬНОСТЬ" />

Серверная пагинация реализуется двумя способами, и разница между ними проявляется на больших объёмах.

Offset-пагинация — это `LIMIT 50 OFFSET 10000`. Чтобы вернуть строки с 10 001-й по 10 050-ю, СУБД должна отсчитать и пропустить первые 10 000 — даже при наличии индекса работа по пропуску растёт линейно с величиной offset. На первых страницах разница незаметна; на глубоких offset деградирует, и переход на страницу 5 000 заметно медленнее перехода на страницу 2. Второй дефект offset — нестабильность под вставками и удалениями: если между запросом страницы 2 и страницы 3 в начало набора добавилась строка, всё сдвигается на одну позицию, и одна запись либо повторяется на границе страниц, либо пропадает.

Cursor-пагинация устраняет оба дефекта. Запрос формулируется как «верни 50 строк, у которых (дата, id) меньше, чем (дата, id) последней виденной строки», и при наличии индекса по этому ключу СУБД сразу прыгает в нужное место — стоимость не зависит от того, насколько «глубоко» в наборе находится позиция. И поскольку курсор привязан к значению конкретной строки, а не к её порядковому номеру, вставки и удаления выше по списку не сдвигают границу: запись не дублируется и не теряется. Цена — курсор не даёт произвольного доступа: нельзя прыгнуть на «страницу 500», можно только идти вперёд (и назад) относительно текущей позиции. Поэтому cursor отлично ложится на infinite scroll и «load more» и плохо — на нумерованную пагинацию с переходом к произвольной странице. Для нумерованной навигации с прыжками по страницам offset остаётся практичным выбором, пока offset не становятся экстремальными.

Виртуализация (рендер только видимых строк, разобранный в предыдущей теме) решает другую задачу — производительность DOM, а не передачи данных, — и комбинируется с любой из стратегий: серверные чанки по cursor, виртуализация внутри загруженного.

<MarginNote>
Ключ курсора должен быть уникальным и совпадать с порядком сортировки. Курсор только по неуникальной дате теряет строки с одинаковой датой на границе чанка — поэтому в ключ добавляют уникальный tie-breaker (id), тот же приём, что обеспечивает стабильность сортировки.
</MarginNote>

<SectionBreak id="07" label="CLIENT-SIDE ПРОТИВ SERVER-SIDE" />

Где выполняются сортировка и фильтрация — в браузере или на сервере — определяется размером набора. Если весь набор уже загружен на клиент и помещается в память без деградации, сортировка и фильтрация делаются в браузере: отклик мгновенный, серверных запросов на каждое действие нет. Это работает на сотнях и единицах тысяч строк — порядок величины зависит от ширины строки и устройства, но грубый ориентир: пока набор измеряется тысячами, а не десятками тысяч, client-side обычно оправдан.

Когда набор слишком велик для передачи и хранения на клиенте, сортировка, фильтрация и пагинация уходят на сервер: каждое действие пользователя превращается в запрос с параметрами `sort`, `filter`, `page`. Браузер показывает только текущий срез. Это неизбежно для десятков и сотен тысяч строк, но добавляет латентность каждому взаимодействию и требует, чтобы серверная сортировка была детерминированной (с tie-breaker) и согласованной с тем, что показывает UI.

Граница не бинарна. Гибрид — серверная пагинация крупными чанками (1 000–5 000 строк) с client-side виртуализацией и сортировкой внутри чанка — частый компромисс: пользователь скроллит чанк непрерывно, а соседние чанки подгружаются в фоне. Решение «client vs server» принимается по объёму и стоимости передачи, и его лучше принять до того, как UI спроектирован под одну модель и упрётся в другую.

<SectionBreak id="08" label="СОСТОЯНИЕ В URL: SHAREABLE VIEWS" />

Сортировка, активные фильтры и текущая страница — это состояние представления, и место для него — query string, а не только память компонента. Когда состояние живёт в URL, отфильтрованное и отсортированное представление становится разделяемым: пользователь копирует ссылку, отправляет коллеге, кладёт в закладку, и тот видит ровно тот же срез. Кнопки «назад» и «вперёд» в браузере начинают работать осмысленно, а перезагрузка страницы не сбрасывает работу.

```text
/orders?status=open&qty_lt=10&supplier=acme&sort=-updated&page=3&size=50
```

Здесь `status`, `qty_lt`, `supplier` — фильтры; `sort=-updated` — сортировка по полю `updated` по убыванию (минус как маркер направления — распространённая конвенция); `page` и `size` — пагинация. Чтение состояния из URL при загрузке и запись обратно при каждом изменении (через History API, обычно `replaceState` для мелких правок, чтобы не засорять историю) делает таблицу детерминированной: один URL — одно представление.

Из этого следует и анти-паттерн: потеря состояния фильтров при навигации. Пользователь отфильтровал набор, открыл запись, вернулся назад — и фильтры сброшены, приходится настраивать заново. Если состояние в URL, возврат восстанавливает его автоматически. Связанный анти-паттерн — неожиданный сброс на первую страницу: смена сортировки или применение фильтра не должны молча перебрасывать на page 1, если пользователь работал на page 7, кроме случаев, когда после фильтрации страницы 7 объективно больше не существует — и тогда переход должен быть очевиден, а не внезапен.

<MarginNote>
Не всё состояние стоит держать в URL: транзиентное (открытый popover, наведённая строка) остаётся в памяти. В query string попадает то, что осмысленно разделять и восстанавливать — фильтры, сортировка, страница, размер страницы.
</MarginNote>

<SectionBreak id="09" label="ACCESSIBILITY ВЗАИМОДЕЙСТВИЯ" />

Сортировка и фильтрация меняют содержимое таблицы динамически, и эти изменения нужно объявлять не только визуально. Заголовки должны быть полностью операбельны с клавиатуры — отсюда `<button>` внутри `<th>`, активируемый Enter и Space, и синхронный `aria-sort`. После сортировки или фильтрации полезно объявить результат через live region (`aria-live="polite"`): «Показано 47 из 1 250 строк», «Отсортировано по дате, убывание». Без этого пользователь screen reader совершает действие и не получает подтверждения, что оно сработало.

Счётчик результата важен вдвойне для незрячих: зрячий видит, что таблица сократилась, а пользователь SR узнаёт об этом только из объявления. Тот же счётчик решает проблему пустого результата — объявление «Ничего не найдено по выбранным фильтрам» сообщает причину, а не оставляет в тишине.

Управление фокусом при смене страницы — отдельный пункт. После перехода на следующую страницу содержимое `<tbody>` полностью заменяется; если фокус оставался на строке, которой больше нет, он «падает» в начало документа. Корректное поведение — переместить фокус на осмысленный якорь: на контейнер таблицы, на первую строку новой страницы или на заголовок региона, — чтобы навигация с клавиатуры продолжилась с предсказуемой точки, а не с верха страницы. Для виртуализованных таблиц фокус, как разбиралось ранее, требует хранения индекса в состоянии и возврата при ремоунте строки.

<SectionBreak id="10" label="АНТИ-ПАТТЕРНЫ И СИНТЕЗ" />

Соберём типовые провалы, каждый из которых ломает базовое ожидание пользователя. Infinite scroll на странице с футером — содержимое футера становится недостижимым, потому что подгрузка вечно отодвигает его вниз. Потеря состояния фильтров при навигации «туда-обратно» — пользователь настраивает срез заново после каждого перехода; лечится хранением состояния в URL. Неожиданный сброс на первую страницу при смене сортировки или фильтра, когда пользователь работал на седьмой. Нестабильная сортировка — строки с равными ключами прыгают местами при каждой пересортировке и на границах страниц; лечится tie-breaker'ом. Слияние фильтра и поиска в один input, дающее то лишние, то недостающие строки. Фильтрация без видимого активного состояния — пользователь ищет строку, которой нет в выдаче, не понимая, что она отфильтрована.

Взаимодействие с таблицей собирается из трёх механизмов и одного решения о том, где живёт состояние. Сортировка меняет порядок и должна быть стабильной, операбельной с клавиатуры и честно объявленной через `aria-sort`. Фильтрация сужает набор по точным условиям, отличается от нечёткого поиска, показывает активное состояние через chips и счётчик и осмысленно ведёт себя при пустом результате. Пагинация выбирается под сценарий: нумерованная — там, где нужен deep linking и переход к произвольной странице; «load more» и infinite scroll — для непрерывного чтения лент без футера; cursor — под большие наборы, где offset деградирует и сдвигается под вставками. И сквозное решение — состояние представления в query string, превращающее таблицу в разделяемый, восстановимый, детерминированный инструмент.

Главное правило то же, что во всей линейке: проверять на реальной нагрузке. Сортировка кажется стабильной на пятидесяти уникальных значениях и рассыпается на тысяче дубликатов; offset кажется быстрым на странице 2 и медленным на странице 5 000; потеря фильтров незаметна на одном экране и невыносима в реальном рабочем цикле «отфильтровал — открыл — вернулся». Профессиональная таблица проектируется под этот цикл, а не под скриншот первой страницы.

<Exercise title="Редизайн: журнал транзакций со сломанным взаимодействием">
  **Описание.** Свободный ответ с конкретными решениями. Вам дают существующую таблицу с набором проблем взаимодействия; нужно диагностировать каждую и предложить исправление, обоснованное сценарием пользователя.

  **Задание.** Финансовый журнал транзакций: ~400 000 строк, пользователь — бухгалтер, работает в таблице ежедневно, регулярно фильтрует по периоду, контрагенту и статусу, открывает отдельные транзакции и возвращается к списку. Текущее поведение: (1) infinite scroll, страница имеет футер с итогами и экспортом, до которого пользователь не доходит; (2) при открытии транзакции и возврате назад фильтры сбрасываются; (3) сортировка по сумме иногда «перемешивает» транзакции с одинаковой суммой при каждом клике; (4) серверная пагинация на `OFFSET`, переход к старым периодам ощутимо тормозит; (5) фильтр и поиск объединены в один input, и точный поиск по номеру документа возвращает лишние строки; (6) после фильтрации пользователь screen reader не понимает, сработал ли фильтр. Опишите для каждого пункта: в чём проблема и как её исправить. Затем спроектируйте URL-схему состояния (фильтры + сортировка + страница) для этого журнала.

  **Критерии оценки.** Хороший ответ закрывает шесть пунктов конкретными решениями.

  (1) **Infinite scroll → нумерованная пагинация (или «load more»).** Страница с футером несовместима с infinite scroll: итоги и экспорт недостижимы. Бухгалтеру нужен deep linking и возврат к конкретному периоду — нумерованная пагинация с размером страницы и URL даёт и то, и достижимый футер.

  (2) **Сброс фильтров → состояние в URL.** Фильтры по периоду, контрагенту, статусу пишутся в query string; открытие транзакции — переход, возврат «назад» восстанавливает URL и фильтры автоматически. Транзиентное состояние в памяти не помогает — нужен именно URL или сопоставимое хранилище, переживающее навигацию.

  (3) **Перемешивание → стабильная сортировка с tie-breaker.** Транзакции с равной суммой прыгают, потому что сортировка нестабильна на сервере. Добавить уникальный ключ (id транзакции или timestamp+id) последним полем `ORDER BY` — порядок становится детерминированным.

  (4) **OFFSET тормозит → cursor-пагинация по ключу.** Старые периоды = большие offset = линейный пропуск. Перейти на курсор по (дата, id) с индексом; для бухгалтера навигация по периодам преимущественно последовательная, произвольный прыжок на «страницу 3000» не нужен, поэтому потеря random-access не критична. Альтернатива — фильтр по периоду, резко сокращающий набор до cursor-запроса.

  (5) **Слияние фильтра и поиска → разделить.** Точный поиск по номеру документа — это фильтр на равенство поля, а не нечёткий поиск по всем колонкам. Развести: явный фильтр «Номер документа =» и отдельный global search для текстового поиска.

  (6) **Молчание для SR → live region.** После фильтрации объявлять результат через `aria-live="polite"`: «Показано N из M» либо «Ничего не найдено по выбранным фильтрам». Заголовки — `<button>` с синхронным `aria-sort`; после смены страницы — перенос фокуса на якорь, а не в верх документа.

  **URL-схема** должна включать фильтры (период `from`/`to`, `counterparty`, `status`), сортировку с направлением (например `sort=-amount`), страницу и размер — нечто вроде `/transactions?from=2026-01-01&to=2026-03-31&counterparty=acme&status=posted&sort=-amount&page=3&size=50`. Дополнительный плюс — упоминание `replaceState` против `pushState` для управления историей и осознание, что транзиентное состояние (открытый popover) в URL не попадает.
</Exercise>
