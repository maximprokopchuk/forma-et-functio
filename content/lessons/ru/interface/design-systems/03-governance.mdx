<DropCap>Д</DropCap>изайн-система живёт между двумя крайностями. На одном полюсе — bottleneck: каждое изменение проходит через выделенную команду, очередь растёт, продуктовые дизайнеры ждут неделями и обходят систему по тихим каналам. На другом — свалка: контрибутит любой без правил, и через год в каталоге четыре кнопки, три модалки и две таблицы, ни одна из которых не совместима с остальными. Governance — набор механизмов, удерживающих рабочую середину: contribution model, SemVer, deprecation policy, adoption tracking, документация. Этот урок — про инфраструктуру, которая позволяет системе оставаться продуктом внутри продукта на горизонте лет.

<SectionBreak id="01" label="СИСТЕМА КАК ПРОДУКТ" />

Главная установка, без которой governance не имеет смысла: дизайн-система — внутренний продукт, а не библиотека-однодневка. У неё есть **consumers** — продуктовые команды, которые собирают из её компонентов экраны и фичи. **Owners** — system team, отвечающая за связность каталога, актуальность документации и миграции при breaking changes. Свой **roadmap**, **support**, **versioning** и **changelog**. И собственный пользовательский опыт: насколько легко найти компонент, понятен ли его API, быстро ли чинятся баги.

Пакет можно опубликовать один раз и переключиться на следующую задачу. Система требует продолжающейся работы: каждое изменение в продуктах рождает запрос на изменение в системе, каждое изменение в системе порождает миграцию в продуктах. Без признания этой петли руководство удивляется, почему «дизайн-систему мы же сделали в 2023», а в 2026 кнопок снова четыре. Ответ простой — её выкатили и оставили без owners.

Из этой рамки следует всё остальное содержание урока. Есть consumers — нужен механизм, через который они приносят запросы (contribution model). Есть выпуски и breaking changes — нужен SemVer. Есть удаления — нужна deprecation policy с предсказуемыми таймлайнами. Есть adoption — нужны метрики. Есть API — нужна документация, на которую API ссылается. Пропуск любого слоя превращает систему обратно в библиотеку.

<SectionBreak id="02" label="CONTRIBUTION MODEL" />

Contribution model — это правило, по которому новый компонент или изменение попадают внутрь системы. На практике встречаются три устойчивых формы.

**Centralized**. Все изменения проходят через выделенную system team. Продуктовый дизайнер описывает потребность в issue, system team планирует, реализует, выпускает версию. Governance простой: качество держится за счёт того, что весь код пишет одна команда. Слабое место — масштабирование. Уже на десяти-пятнадцати продуктовых дизайнерах system team превращается в bottleneck, очередь растёт быстрее, чем команда успевает её разбирать, и продуктовые дизайнеры начинают писать локальные «временные» компоненты. Centralized работает до десяти продуктовых дизайнеров; дальше — нет.

**Federated**. Контрибутить может любой, всё проходит через ревью system team. Продуктовый дизайнер открывает PR в репозиторий системы; CI запускает visual regression (Chromatic, Percy), accessibility-чеки (axe), token-валидацию, типы и тесты; system team ревьюит дизайн и API, проверяет, что компонент не дублирует существующий; merge. Federated требует двух вещей: сильной дисциплины ревью и зрелого CI. Без автоматических чеков ревью становится визуальной приёмкой, которая не масштабируется. Federated работает на крупных организациях — пятьдесят и более product designers, — где иначе очередь к system team становится политической проблемой.

**Solitary** — третий случай, более частый, чем хотелось бы. Один человек тянет систему «по доброй воле» рядом с основной продуктовой работой. На горизонте трёх-шести месяцев это даёт результат. На горизонте года-двух solitary заканчивается одним из двух способов: человек сгорает или уходит. Анти-паттерн на длинной дистанции; руководство, выбирающее его сознательно («у нас нет бюджета на system team»), выбирает потерю системы через два года.

Зрелые компании работают по гибриду. Tokens — federated (любой может предложить новый semantic-токен), потому что токенов много и system team не успевает за всеми. Компоненты — centralized (только system team пишет и поддерживает), потому что компоненты — точка, где сходятся API, доступность, темизация и документация. Material 3 и IBM Carbon работают именно так; у Polaris и Spectrum модели мягче, но логика та же. Гибрид сохраняет скорость на токенах и качество на компонентах.

<MarginNote>
Nathan Curtis, EightShapes (medium.com/eightshapes-llc) — серия статей про contribution models с 2014 года; именно у него индустрия взяла словарь «centralized / federated / solitary» и описание их пределов масштабирования.
</MarginNote>

<SectionBreak id="03" label="VERSIONING" />

SemVer — semantic versioning — это стандарт, по которому номер версии `MAJOR.MINOR.PATCH` коммуницирует характер изменений. Для дизайн-системы он работает так же, как для любого пакета.

**Major** — breaking change. Token переименован (`color/brand/primary` → `color/action/primary`), компонент удалён, prop сменил имя или сигнатуру, default-значение изменилось так, что зависящий от него код сломается. Major-релиз требует от потребителя ручной работы: пройти по всем местам использования и переписать. На крупной кодовой базе это месяцы, и без поддержки со стороны системы команды откладывают upgrade — иногда на годы.

**Minor** — добавление, обратно совместимое. Новый компонент, новый variant у существующего компонента, новый token в семантическом слое, новая опциональная prop с разумным default'ом. Потребитель может обновиться без изменений в собственном коде; новые возможности доступны там, где он захочет ими пользоваться.

**Patch** — bug fix или визуальная правка, не меняющая API. Исправлен offset фокусного кольца, поправлен contrast у `text/secondary` в тёмной теме, починен edge-case в keyboard navigation. Потребитель обновляется автоматически, без раздумий.

Ритмы релизов разнятся. Material 3 выпускает major раз в два-три года, с большими migration guide'ами. Polaris выпускает minor примерно раз в месяц, major — реже. IBM Carbon работает по SemVer с версии 10.0 (2018); публичный changelog показывает аккуратное разделение между major, minor и patch. Наблюдение: чем зрелее система, тем длиннее цикл major'ов и тем плотнее minor'ы.

Ключевая практика, без которой SemVer не работает на крупной кодовой базе, — **codemod**. Вместе с breaking change system team публикует автоматический скрипт, который проходит по коду потребителя и переписывает старый API на новый. Базовые инструменты — `jscodeshift` от Facebook и `@codemod/cli`; для CSS/Sass-токенов — собственные ast-парсеры или `postcss`. Codemod заменяет `<Button type="primary">` на `<Button variant="primary">` во всех файлах продукта одной командой; без него команды откладывают upgrade на месяцы и годы. Система при этом фрагментируется: разные продукты находятся на разных major'ах, поддержка вынуждена работать одновременно с двумя-тремя версиями. Codemod — обязательная часть pull request с breaking change. Material UI, Chakra, Stripe этот контракт держат строго.

<SectionBreak id="04" label="DEPRECATION POLICY" />

Удаление компонента или token — операция, более деликатная, чем добавление. Любое удаление — breaking change у всех потребителей; вопрос только в том, как этот breaking сообщён и сколько времени дано на миграцию. Зрелая deprecation policy состоит из трёх шагов: **announce**, **warn**, **remove**.

**Announce**. В changelog публикуется запись: «Компонент `LegacyTabs` помечен как deprecated; будет удалён в версии X.0 (примерно через двенадцать месяцев). Используйте `Tabs`; codemod доступен здесь». Параллельно — анонс в Slack-канале системы и email-рассылка по контактам команд. Молчаливое deprecation — анти-паттерн: команды узнают об удалении в момент, когда оно их ломает.

**Warn**. В коде добавляется сигнал, что использование устарело. Runtime — `console.warn` в dev mode при первом монтировании. Типы — JSDoc-аннотация `@deprecated` с указанием замены; IDE подсвечивает такой импорт зачёркиванием. Линтер — кастомное правило в `eslint-plugin-design-system`, которое падает на CI и блокирует merge нового кода с deprecated-импортами.

**Remove**. Финальное удаление откладывается не меньше, чем на шесть месяцев — год после announce. Material 3 проводит цикл за двенадцать-восемнадцать месяцев, IBM Carbon — за шесть-двенадцать, Polaris — за шесть. Меньше шести месяцев — недостаточно: команды не успевают встроить миграцию в собственный roadmap.

Дополнительный слой — **tracking deprecated usage**. System team держит бот или CI-задачу, которая сканирует репозитории потребителей на импорты deprecated-компонентов и открывает issue с напоминанием о таймлайне. Без такого механизма deprecated-импорты живут годами после announce, и в момент remove оказывается, что половина продуктов всё ещё на старом API.

Без deprecation policy любое удаление превращается в политический инцидент: команды ругаются, удаление откатывается, в каталоге накапливается мёртвый код. С policy — удаление становится плановой операцией, ожидаемой за год.

<SectionBreak id="05" label="ADOPTION TRACKING" />

Adoption — степень, в которой продукты реально пользуются системой. Без измерения adoption governance работает вслепую: system team не знает, какие компоненты востребованы, какие проигнорированы, какие переписаны локально. Метрики, которые имеет смысл считать, — четыре.

**Процент продуктов на последней версии.** Восемь из десяти на последнем major'е, два — на предыдущем — здоровое распределение; три на последнем, остальные размазаны по четырём предыдущим — сигнал, что migration-tooling не работает. **Процент компонентов из системы vs реинвентированных.** Доля UI-элементов из системы против собственных локальных. Целевой показатель зрелой системы — выше восьмидесяти процентов. **Ratio token usage vs hardcoded values.** Сколько цветов и отступов берётся из токенов, сколько хардкодится числами. Сорок процентов хардкода — система не работает; десять и ниже — норма. **Coverage документации**. Какой процент компонентов имеет полный набор stories, usage rules, don'ts. Дыра в документации почти всегда соответствует дыре в adoption.

Реализация — техническая. Salesforce SLDS использует SLDS Validator — линтер, считающий совпадения с системными классами. Spotify — собственный sandboxed CI, собирающий статистику использования. IBM Carbon держит внутренний дашборд adoption. Минимально жизнеспособный вариант — `eslint-plugin-design-system` с кастомными правилами: «hardcoded color», «non-system component import», «deprecated import». Линтер выдаёт цифры, цифры собираются в дашборд, дашборд читается раз в квартал.

Отдельный сюжет — **тёмная сторона adoption: реинвент**. Команда пишет собственный `Modal` вместо системного. Причин ровно три. Первая — системный компонент плохой: API неудобный, поведение не покрывает реальный кейс, доступность сломана. Чинить нужно системный, а не наказывать команду. Вторая — компонент плохо документирован: команда о нём не знала или не нашла нужный variant. Чинить нужно документацию. Третья — нужны кастомизации, которых в системе нет. Расширить нужно систему — добавить slot, variant или prop, который покрывает кейс. Реинвент — почти всегда сигнал о пробеле в системе, не о недисциплинированности команды. System team, воспринимающая реинвент как нарушение, теряет доверие; команда, воспринимающая его как input для собственного roadmap, выигрывает.

<MarginNote>
Brad Frost в *Design Systems* (Atomic Design, 2016) и в публичных выступлениях после неё несколько раз формулировал тезис: «Если команды обходят твою систему, проблема в системе, а не в командах». Это базовая установка для тех, кто читает adoption-метрики и не делает выводов в духе «нужно жёстче запретить».
</MarginNote>

<SectionBreak id="06" label="ДОКУМЕНТАЦИЯ" />

Документация — поверхность, через которую система встречается с потребителем. Если её нет или она устарела, всё остальное работает в полсилы: компонент может быть написан образцово, но если его нельзя найти и понять за пять минут, продуктовый дизайнер напишет свой. Зрелая документация состоит из трёх уровней.

**Уровень 1 — Storybook.** Visual playground, в котором каждый компонент показан во всех variant'ах и состояниях. Stories — отдельные сцены: `<Button variant="primary">`, `<Button state="loading">`, `<Button variant="destructive" size="sm">`. Storybook автоматически генерирует controls — UI, через который ревьюер подкручивает props и видит результат. Первый touch-point: дизайнер или инженер заходит, ищет компонент, видит, как он выглядит, решает, подходит ли.

**Уровень 2 — MDX docs.** Поверх Storybook (с версии 7 нативно) или на отдельном сайте — текстовая документация с usage rules. «Когда использовать `Modal`: для критических подтверждений, требующих явного решения. Когда **не** использовать: для уведомлений (`Toast`), второстепенных подтверждений (`Popover`), длинных форм (отдельный экран)». Этот уровень превращает компонент из набора props в часть системы языка. Без MDX-уровня каталог остаётся набором изолированных сцен, в котором непонятно, какой компонент брать.

**Уровень 3 — Don'ts.** Раздел с явно перечисленными ошибками применения, желательно с визуальными примерами «правильно / неправильно». «Не используйте `Modal` для toast-уведомлений». «Не используйте `Button variant="destructive"` для cancel-действий — destructive зарезервирован под необратимые операции». «Не вкладывайте `Card` в `Card`». Без явных don'ts компонент за полгода обрастает пятью кривыми применениями: команды, не получившие «нельзя», ставят его в любое подходящее по виду место. Don'ts — самая дешёвая часть документации в производстве и самая дорогая в отсутствие.

Отдельная боль — синхронизация Figma-библиотеки и кодового репозитория. **Контракт** в зрелой системе: Figma и код — две стороны одного объекта. Расхождение — баг, не норма. Инструменты, которые делают синхронизацию реальной, — Tokens Studio (плагин Figma, экспортирующий токены в формат для Style Dictionary), Storybook Connect (связывает Figma-фрейм со story), Specify, Supernova. Без синхронизации дизайнер рисует то, чего нет в коде, или инженер собирает компонент по двухлетнему макету. Контракт держится не словами, а tooling'ом.

Образцы публичной документации: Polaris (polaris.shopify.com) — образцовый MDX-уровень, с разделами «when to use», «when not to use», «do/don't»; Atlassian Design System (atlassian.design) — сильный playground и token documentation; Adobe Spectrum (spectrum.adobe.com) — продуманная навигация. Все три дают рабочий ориентир.

Jina Anne, бывший lead дизайн-системы Salesforce Lightning, — автор Style Dictionary и один из ключевых голосов индустрии по theming-governance. *Design Systems Handbook* (DesignBetter.co, InVision, 2017) — её соавторская работа с Marco Suarez, Katie Riley, Tim Van Damme и Jeremy Sykes — до сих пор остаётся хорошей входной точкой для тех, кто строит документацию системы впервые.
</MarginNote>

<SectionBreak id="07" label="СИНТЕЗ" />

Три темы трека складываются в одну архитектуру. **Tokens** — нижний слой: имена, под которыми живут значения, и семантика, позволяющая менять реализацию без переписывания компонентов. **Component API** — средний слой: контракт между компонентом и потребителем, в котором variants, slots, polymorphism и controlled/uncontrolled задают сетку проектирования. **Governance** — верхний слой: инфраструктура, удерживающая первые два слоя живыми во времени. Без токенов API ссылается в пустоту. Без API governance управляет компонентами без внутренней дисциплины. Без governance токены и API через год теряют связность.

Связь работает в обе стороны. Контрибуция в federated-модели проверяет одновременно три слоя: что компонент использует semantic-tokens (token-валидация); что его API следует принципам трека (variant — закрытый union, controlled/uncontrolled разделено); что документация полная (stories, MDX usage rules, don'ts). SemVer-релиз ссылается на token-наслоение: minor может добавить semantic-token, major — переименовать существующий. Deprecation policy завязана на codemod, codemod пишется на основе явного API. Каждый слой держит остальные.

Главное отличие системы от библиотеки — продолжающаяся работа. Библиотека выпускается и забывается. Система требует постоянного потока: запросы консьюмеров, ревью контрибуций, релизы по SemVer, deprecation-циклы, обновление документации, измерение adoption. Это не побочная нагрузка system team; это её основная работа. Попытка «оптимизировать» governance до нуля («давайте просто договоримся аккуратно использовать») приводит к одному результату через двенадцать-восемнадцать месяцев: каталог в виде свалки, продукты рассинхронизированы, доверие исчерпано.

После трека — два направления. Первое — масштабирование на несколько брендов и продуктов: multi-brand theming поверх семантического слоя, federated governance на уровне организации, cross-product migration. Второе — стык с design-ops: как контрибуция в систему вписывается в продуктовый roadmap, как система участвует в quarterly planning, как office hours встроены в общую ритм-сетку. Оба направления оперируют объектами, которые трек уже определил: token, компонент, версия, deprecation, adoption-метрика.
