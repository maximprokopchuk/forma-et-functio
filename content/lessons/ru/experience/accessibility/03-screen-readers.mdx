<DropCap>З</DropCap>рячий дизайнер, впервые включивший screen reader, обычно ожидает услышать «озвученный текст страницы». Это первое и главное недоразумение. Screen reader — не синтезатор речи поверх рендеринга и не озвучка визуального макета. Это отдельный движок, который читает не пиксели и не DOM напрямую, а *accessibility tree* — дерево семантических объектов, которое браузер собирает из DOM, фильтрует и обогащает данными о ролях, состояниях и именах. Если элемент в это дерево не попал — для пользователя screen reader его не существует, как бы выразительно он ни выглядел на экране.

Эта тема — про инструмент, через который значительная часть пользователей a11y воспринимает интерфейс. Три основных движка и их привычки. Семантический HTML как 80–90% всей доступности и ARIA как узкое исключение. Landmark-роли и навигация, в которой Tab — не главный шорткат. Live regions для динамических обновлений, на которых ломается почти каждый современный SPA. Focus management — отдельная дисциплина, которая решает, продолжается ли сценарий или обрывается. И в конце — практический протокол тестирования: что и в каком порядке делать с VoiceOver или NVDA, чтобы не сдавать в продакшен интерфейс, который слышен как мусор.

<SectionBreak id="01" label="SR ЧИТАЕТ ACCESSIBILITY TREE, А НЕ ТЕКСТ" />

Современный браузер строит две параллельные структуры. Первая — DOM, привычное дерево HTML-элементов, по которому работают CSS, JavaScript и DevTools Inspector. Вторая — *accessibility tree*, отдельная структура, которую браузер собирает на основе DOM, но не идентичная ему. В accessibility tree попадают только те узлы, которые имеют семантическое значение: интерактивные элементы, контент, заголовки, landmark-регионы. Чисто декоративные обёртки, презентационные `div` без роли, скрытые через `aria-hidden` или `display: none` поддеревья — отфильтровываются.

Каждый узел accessibility tree хранит четыре основных свойства: **role** (роль — кнопка, ссылка, заголовок, регион), **name** (имя, доступное программно — то, что screen reader произнесёт первым), **value** (значение — для чекбоксов, инпутов, слайдеров) и **state** (состояние — focused, checked, expanded, disabled, busy). Screen reader не читает innerText; он перечисляет узлы accessibility tree и для каждого собирает реплику из этих четырёх полей в порядке, который зависит от типа объекта и режима навигации.

Из этой архитектуры вытекает следствие, которое для зрячего дизайнера выглядит контринтуитивным. `<button>Сохранить</button>` и `<div onClick={save}>Сохранить</div>` в браузере выглядят почти одинаково — одинаковый текст, одинаковая позиция, оба реагируют на клик мышью. В accessibility tree это два принципиально разных объекта. Первый — узел с role «button», name «Сохранить», state «focusable». Screen reader произнесёт «Кнопка, Сохранить», JAWS-пользователь услышит, что элемент активируется по Enter или Space, попадёт в Tab-цепочку автоматически, обработается шорткатом B (next button) в NVDA. Второй — текстовый узел внутри generic-контейнера. Никакой роли, никакого name отдельно от текста, не попадает в Tab-цепочку, не находится через шорткаты для интерактивных элементов. Для пользователя screen reader второй вариант — не «кнопка, выглядящая как div», а просто текст «Сохранить» в потоке параграфа.

<MarginNote>
Accessibility tree формализован в спецификации Core Accessibility API Mappings (W3C, последняя редакция Core-AAM 1.2, 2023). Браузер преобразует DOM в платформенный accessibility API: UIA на Windows, AX API на macOS, ATK/AT-SPI в Linux. Screen reader общается с этим API, не с браузером напрямую.
</MarginNote>

Эта же логика объясняет, почему «визуально кнопка» — недостаточное условие. Можно стилизовать `<a>` под кнопку через CSS — но семантически это останется ссылка, которая активируется по Enter, не по Space, и даёт screen reader команду «перейти». Можно стилизовать `<div role="button" tabindex="0">` — и формально это даст роль и focusability, но ровно потому, что мы вручную восстановили то, что встроено в `<button>` бесплатно. Любая сложная разработка accessibility начинается с того, что разработчик понимает: SR работает на отдельном уровне абстракции, и решения, принятые на этом уровне, не отменяются ни CSS, ни JavaScript-ом, ни «дизайнерским намерением».

<SectionBreak id="02" label="ТРИ ДВИЖКА И ИХ ПРИВЫЧКИ" />

Среди скринридеров доминируют три имени, и за каждым стоит своя история, свои клавиатурные привычки и свой профиль пользователей. Карта рынка важна для тестирования: проверка с VoiceOver не равнозначна проверке с NVDA, несмотря на то что оба читают одно и то же accessibility tree.

**JAWS** (Job Access With Speech) — самый старый из трёх, выпущен Henter-Joyce в 1995 году, с 2000-х развивается под брендом Freedom Scientific (сегодня — часть Vispero). Коммерческий продукт, лицензия в районе тысячи долларов, исторически — стандарт корпоративной среды и государственного сектора в США. В JAWS большой набор собственных «virtual cursor»-режимов, продвинутая поддержка форм и таблиц, специфические озвучки, к которым enterprise-пользователи прирастают за десятилетия. Для разработчика JAWS — самый сложный для тестирования движок: дорогой, только Windows, со своим набором квирков; в большинстве команд его держат как контрольную точку перед релизом, но не как ежедневный инструмент.

**NVDA** (NonVisual Desktop Access) — open-source, австралийский фонд NV Access, основан Michael Curran и James Teh в 2006 году. Бесплатный, активно развивается, доля среди пользователей растёт каждый год по данным WebAIM Screen Reader User Survey (исследование выходит регулярно с 2009 года, последнее на момент написания — Survey #10, опубликовано в 2024 году). В Survey #10 распределение primary screen reader среди респондентов выглядит так: JAWS — около половины, NVDA — около трети, VoiceOver на macOS и iOS вместе — около пятой части. Цифры из года в год сдвигаются, общий тренд — NVDA сокращает разрыв с JAWS, VoiceOver удерживает мобильный сегмент. Для разработки NVDA — практический минимум: бесплатный, ставится за минуту, поведение во многом близко к JAWS, что позволяет одной проверкой покрыть значительную долю Windows-пользователей.

**VoiceOver** — встроенный screen reader Apple. Дебютировал в Mac OS X Tiger (10.4, апрель 2005), на iPhone — с iOS 3 (2009). Единственный screen reader на macOS и iOS; альтернатив на платформе нет, что делает его поведение де-факто стандартом для всей Apple-экосистемы. Активируется на Mac шорткатом Cmd+F5, на iPhone — тройным нажатием боковой кнопки или через Settings → Accessibility. У VoiceOver собственная модель навигации с «VO-cursor» (по умолчанию VO = Caps Lock или Control+Option), отдельный rotor для быстрого переключения между типами элементов, специфическая озвучка ролей. Для тестирования веб-продукта на Apple-платформах — обязательный движок; пропускать его в матрице нельзя, потому что у Mac/iOS-пользователей других вариантов нет.

**TalkBack** — screen reader Google для Android, поставляется с Android 1.6 (Donut, 2009). Долгое время отставал по качеству от VoiceOver, но к 2020-м подтянулся; для веб-продуктов с заметной мобильной аудиторией на Android — стоит включать в матрицу хотя бы периодически.

<MarginNote>
WebAIM Screen Reader User Survey — серия исследований, проводимая WebAIM (центр accessibility при Utah State University) с 2009 года. Survey #10 опубликован в 2024 году. Конкретные доли движков из года в год меняются, но порядок устойчив: JAWS лидирует, NVDA близко, VoiceOver за счёт Apple-устройств держит третью позицию. Точные числа стоит проверять перед цитированием.
</MarginNote>

Общее у всех трёх — они читают то же самое accessibility tree, которое строит браузер. Разница — в клавиатурных привычках, голосе по умолчанию, наборе шорткатов, скорости речи. Хорошо построенная семантика будет одинаково озвучена и в JAWS, и в NVDA, и в VoiceOver; плохая семантика сломается во всех трёх, просто слегка по-разному.

<SectionBreak id="03" label="СЕМАНТИЧЕСКИЙ HTML — 80–90% ДОСТУПНОСТИ" />

Существует индустриальная мантра, которую W3C ARIA Authoring Practices фиксируют как **Rule 1 of ARIA**: «No ARIA is better than bad ARIA». Не «ARIA полезен» и не «ARIA плох» — а буквально: отсутствие ARIA лучше, чем неправильный ARIA. Heydon Pickering, один из главных популяризаторов этой формулы, в книгах *Inclusive Design Patterns* (Smashing Magazine, 2016) и *Inclusive Components* (2017) показывает её на десятках конкретных компонентов: правильно собранный нативный HTML почти всегда даёт лучший результат, чем самописный виджет, обвешанный ARIA-атрибутами.

Цифра, которую часто называют, — **80–90% доступности достигается отсутствием ARIA**. Не потому что ARIA вредна сама по себе, а потому что нативные HTML-элементы уже несут роль, имя, фокус и клавиатурное поведение, встроенные в браузер, проверенные миллиардами часов реального использования и согласованные между всеми движками. Ручная сборка тех же свойств — это десять мест, в каждом из которых легко ошибиться, и одна ошибка из десяти ломает весь компонент.

Контрпример — стандартный антипаттерн «div-кнопка»:

```html
<div
  role="button"
  tabindex="0"
  aria-label="Сохранить"
  onclick="save()"
  onkeydown="if (event.key === 'Enter' || event.key === ' ') save()"
>
  Сохранить
</div>
```

Здесь воспроизведено почти всё, что делает `<button>` бесплатно: роль, focusability, доступное имя, клик, обработка Enter и Space. Но «почти всё» — не «всё». Не учтена обработка `event.preventDefault()` для Space (без неё страница проскроллится при нажатии). Не учтено, что Space должен срабатывать на keyup, а не на keydown, чтобы соответствовать поведению нативной кнопки. Не учтено состояние `:disabled` через `aria-disabled` (и связанное с ним блокирование handler-а). Не учтено отсутствие у `div` встроенной поддержки `form="..."` и автоматического `type="submit"` внутри формы. По исследованиям Deque, около 80% кастомных компонентов с самописным `role="button"` имеют как минимум одну такую ошибку. И это всё — чтобы заменить десять символов:

```html
<button onclick="save()">Сохранить</button>
```

Тот же принцип работает для дюжины компонентов, которые исторически собирались вручную, а сегодня имеют нативные HTML-аналоги:

- `<dialog>` — нативная модалка с встроенным focus trap и backdrop. HTML 5.2, кросс-браузерная поддержка с 2022 года: Chrome 37 (2014), Safari 15.4 (март 2022), Firefox 98 (март 2022). До 2022-го приходилось собирать через `role="dialog"` + ручной focus trap; сегодня — `<dialog>` плюс `dialog.showModal()`.
- `<details>` и `<summary>` — нативный collapsible-блок без JavaScript. HTML5.1, реализован всеми major браузерами с ~2016 года. Автоматическое управление состоянием expanded, корректная озвучка screen reader.
- `<nav>`, `<main>`, `<aside>`, `<header>`, `<footer>` — landmark-элементы, формирующие структуру страницы (об этом — следующий раздел).
- `<figure>` и `<figcaption>` — изображение с подписью, программно связанные. SR читает caption как часть имени figure, не как отдельный текст рядом.
- `<output>` — элемент для результата вычисления формы. Имеет встроенный `role="status"`, что делает его live region без дополнительной разметки.

ARIA остаётся уместной в строго определённых ситуациях. Когда нет нативного эквивалента (`role="tablist"` для табов, `role="tree"` для дерева — нативных HTML-элементов под эти паттерны нет). Когда нужно дополнить семантику нативного элемента состоянием, которое HTML не передаёт (`aria-expanded` на кнопке, открывающей меню; `aria-current="page"` на ссылке текущего раздела). Когда нужно создать виртуальную связь между несвязанными в DOM элементами (`aria-describedby` от инпута к hint-тексту, `aria-controls` от триггера к управляемому им регион). Везде остальное — нативный HTML практически всегда выигрывает.

<MarginNote>
W3C WAI-ARIA Authoring Practices, последняя версия 1.2 (2023). Содержит каноническую формулировку «No ARIA is better than bad ARIA» и подробные паттерны для виджетов, у которых нет нативного HTML-эквивалента. Heydon Pickering — *Inclusive Design Patterns* (Smashing Magazine, 2016) и *Inclusive Components* (2017) — два практических компендиума на ту же тему.
</MarginNote>

<SectionBreak id="04" label="LANDMARK-РОЛИ И НАВИГАЦИЯ" />

Зрячий пользователь сканирует страницу глазами: за полсекунды находит хедер, шапку с поиском, основной контент, сайдбар. Screen reader-пользователь делает то же самое — но не глазами, а шорткатами. И ему нужно, чтобы страница имела структурный каркас, по которому эти шорткаты работают.

Главные клавиатурные команды для навигации (на примере NVDA в browse mode):

- **D** — следующий landmark (region, navigation, main, banner, contentinfo).
- **H** — следующий heading; **1**–**6** — следующий heading конкретного уровня.
- **F** — следующее поле формы; **B** — следующая кнопка; **K** — следующая ссылка.
- **T** — следующая таблица; **L** — следующий list; **G** — следующее изображение.
- **Tab** — следующий interactive element (focusable).

Это не редко используемые шорткаты. По данным WebAIM Survey, навигация по заголовкам и landmark — основной способ ориентации на странице у опытных пользователей screen reader. Чтение последовательно сверху вниз — режим, который включают только при первом знакомстве с незнакомой страницей или при чтении длинного документа.

Чтобы эти шорткаты работали, страница должна иметь **landmark-роли**, формирующие её структурный скелет. ARIA определяет восемь:

- `banner` — шапка сайта, обычно один на страницу. Нативно соответствует `<header>` верхнего уровня.
- `navigation` — навигационная зона. Нативно — `<nav>`. На странице может быть несколько (главная навигация, footer-навигация, breadcrumbs); каждой стоит дать `aria-label` для различения.
- `main` — основной контент страницы. Нативно — `<main>`, обязан быть один.
- `contentinfo` — нижняя инфо-зона, footer. Нативно — `<footer>` верхнего уровня.
- `complementary` — дополнительный контент сбоку, часто sidebar. Нативно — `<aside>`.
- `region` — произвольный значимый блок, требующий `aria-label` или `aria-labelledby`.
- `search` — зона поиска (нативного HTML-аналога нет, ставится через `role="search"` на `<form>` или `<div>`).
- `form` — форма с программно заданным именем (если у формы есть `aria-label` или `aria-labelledby`).

Страница без landmark — для screen reader-пользователя одна большая «непроходимая» зона. Шорткат D ничего не находит, навигация распадается на «листать всё подряд». Время на ту же задачу растёт в три-пять раз, и пользователь это запоминает: сайт без структуры воспринимается как «непригодный к работе», даже если визуально выглядит современно.

Параллельная по логике структура — **иерархия заголовков**. `<h1>`–`<h6>` для screen reader — это не просто крупный текст, а навигационная карта. Опытный пользователь, попав на новую страницу, нажимает H несколько раз подряд, чтобы услышать «оглавление» — h1 страницы, h2 основных секций, h3 подсекций. Если иерархия использована для типографики («давайте сделаем h2, потому что нам нужен крупный текст»), карта рассыпается; если на странице нет h1 или вместо `<h2>` стоит `<div class="title-large">`, пользователь теряет ориентацию.

<MarginNote>
WAI-ARIA фиксирует восемь landmark-ролей. Шесть из них имеют нативные HTML-аналоги (`header`, `nav`, `main`, `aside`, `footer`, `form` с именем); две — `search` и `region` — задаются только через ARIA. Принцип: использовать нативный HTML, ARIA добавлять только там, где нативного нет.
</MarginNote>

Практическое правило: каждая страница должна иметь как минимум `<header>` (banner), `<nav>` (navigation, можно несколько с разными `aria-label`), `<main>` и `<footer>` (contentinfo). Заголовки — последовательно, без скачков уровней, h1 один на страницу. Это не «accessibility отделка», это базовая HTML-гигиена, которую legacy-кодовая база нарушает по инерции, а новый продукт обязан соблюдать с первого коммита.

<SectionBreak id="05" label="LIVE REGIONS И ДИНАМИКА" />

Главный pitfall современного SPA: контент в DOM меняется, screen reader ничего не сказал. Пользователь нажал «Сохранить», ответ пришёл, в правом нижнем углу появился toast «Заказ оформлен», через три секунды — редирект на страницу подтверждения. Зрячий увидел toast, услышал короткую анимацию, понял, что всё прошло. Screen reader-пользователь не услышал ничего: фокус остался на кнопке, toast появился где-то за пределами фокуса, страница «молча» сменилась. Сценарий с точки зрения screen reader не завершён — пользователь не знает, что произошло.

Решение — **live regions**, механизм ARIA, через который SR узнаёт об изменениях в определённых частях DOM и автоматически их озвучивает. Атрибут `aria-live` принимает три значения:

- `aria-live="off"` — дефолт, изменения не озвучиваются.
- `aria-live="polite"` — изменения объявляются в первый удобный момент (когда SR закончит текущую реплику).
- `aria-live="assertive"` — изменения объявляются немедленно, прерывая текущую речь.

Параллельно существуют две роли-пресета: `role="status"` эквивалентен `aria-live="polite"`, а `role="alert"` — эквивалентен `aria-live="assertive"`. На практике их и используют: `<div role="status">` для toast и обычных уведомлений, `<div role="alert">` для критических ошибок и системных сбоев.

```html
<div role="status" aria-live="polite">
  {orderStatus}
</div>
```

Сценарии, в которых live region обязателен:

- **Toast-уведомления** — «Сохранено», «Файл загружен», «Заказ оформлен». Любое появление информации без изменения фокуса.
- **Валидационные ошибки форм** — «Введите дату в формате DD.MM.YYYY», появляющееся при потере фокуса с инпута.
- **Обновление счётчиков** — «5 непрочитанных сообщений», появляющееся в реальном времени.
- **Состояния асинхронных операций** — «Загрузка...», «Сохранено», «Ошибка соединения».
- **Результаты автокомплита** — «Найдено 12 предложений», когда выпадает список после ввода.

У live region есть несколько подводных камней, из-за которых их часто реализуют неправильно.

**Контейнер должен существовать в DOM до того, как туда попадёт текст.** Это не очевидно. Многие реализации создают `<div role="alert">{message}</div>` динамически: появилось сообщение — добавили div с текстом. Большинство screen reader не услышат это объявление: они подписываются на изменения существующих live regions, не на появление новых. Правильный паттерн — пустой контейнер всегда в DOM, текст вставляется внутрь:

```jsx
function ToastRegion({ message }) {
  return (
    <div role="status" aria-live="polite" aria-atomic="true">
      {message}
    </div>
  );
}
```

`aria-atomic="true"` — отдельная тонкость: говорит SR читать всё содержимое контейнера, а не только diff. Без этого если в контейнере было «5 сообщений», и оно изменилось на «6 сообщений», некоторые SR прочитают только «6», теряя контекст.

**Assertive — только для критичного.** Соблазн поставить `role="alert"` на каждое уведомление велик: «пусть точно услышит». Но assertive прерывает текущую речь: пользователь, который слушал название кнопки, услышит обрывок, а потом сразу alert. Если alerts срабатывают часто, они становятся фоновым шумом, а основной flow — невозможным. Assertive оправдан для critical errors («Соединение потеряно, ваши изменения могут не сохраниться»), не для подтверждений и счётчиков.

**Не дублировать содержимое.** Если форма валидирует поле и показывает ошибку через `aria-describedby` или связанный hint, дополнительно объявлять её через live region не нужно — SR прочитает её при возврате фокуса на поле. Дублирование приводит к двойному озвучиванию: пользователь слышит ошибку дважды и теряет терпение.

WCAG 2.1 формализует это требование как SC 4.1.3 «Status Messages» (Level AA): статусные сообщения должны быть программно объявляемыми без перемещения фокуса. Live region — стандартный способ выполнить этот критерий.

<MarginNote>
WCAG 2.1 SC 4.1.3 «Status Messages» (Level AA, 2018) — критерий, требующий, чтобы изменения статуса (успех, ошибка, прогресс) были программно объявлены без перемещения фокуса пользователя. ARIA `aria-live`, `role="status"`, `role="alert"` — стандартные механизмы выполнения этого требования.
</MarginNote>

<SectionBreak id="06" label="FOCUS MANAGEMENT" />

Focus — это место, где находится курсор клавиатуры. Для зрячего пользователя focus важен, но не централен: можно навигироваться мышью, focus используется только при работе с клавиатурой. Для screen reader-пользователя focus и virtual cursor — два разных механизма, которые тесно связаны: SR озвучивает то, что в фокусе или то, на что наведён virtual cursor, и поведение focus определяет, продолжается ли сценарий или обрывается.

Базовые требования к focus, формализованные в WCAG:

- **2.1.1 Keyboard** (Level A) — все интерактивные элементы достижимы клавиатурой. Tab/Shift+Tab переключают фокус, Enter/Space активируют, Escape закрывает.
- **2.4.3 Focus Order** (Level A) — порядок Tab-навигации соответствует визуальному порядку и логике контента. Вертикальная форма читается сверху вниз, не «через два поля и обратно».
- **2.4.7 Focus Visible** (Level AA) — focus всегда визуально различим. Браузерный default-outline можно стилизовать, но не отключать; `outline: none` без замены — одна из самых частых ошибок.

Поверх этих базовых требований лежит специальный класс задач — **focus management в модалках и сложных компонентах**. Когда открывается модальное окно, нужно сделать три вещи:

1. **Перевести focus внутрь модалки.** Обычно — на первое интерактивное поле или на сам контейнер модалки (если он имеет `tabindex="-1"` и `role="dialog"`).
2. **Поймать focus внутри (focus trap).** Tab из последнего элемента модалки должен возвращаться к первому, Shift+Tab из первого — к последнему. Tab не должен «утекать» в фоновую страницу.
3. **При закрытии — вернуть focus на trigger.** Кнопка, открывшая модалку, должна получить focus обратно после закрытия. Иначе фокус «теряется» (обычно сбрасывается на body), и пользователь оказывается в начале страницы.

Реализовывать focus trap руками — задача, в которой легко ошибиться: нужно учитывать все типы интерактивных элементов, динамически добавляющиеся, скрытые через `hidden` или `display: none`, кастомные `tabindex`. Поэтому в production обычно используют проверенные библиотеки.

- **focus-trap** (David Clark, open-source, активно поддерживается с середины 2010-х) — vanilla-библиотека для focus trap, framework-agnostic. Версия для React — `focus-trap-react`. Работает с любым модальным контейнером.
- **react-aria** (Adobe Spectrum, open-source с 2020 года) — набор хуков для accessible-компонентов, включая `useFocusTrap`, `useDialog`, `useModalOverlay`. Фундаментальное преимущество — полное покрытие accessibility-кейсов, проверенное командой Adobe на их собственных продуктах.
- **Radix UI** (open-source с 2020 года, в 2024 году WorkOS-acquired) — набор unstyled accessible-компонентов для React. `Dialog`, `Popover`, `DropdownMenu` приходят с встроенным focus management, focus trap, корректным `role`, ARIA-атрибутами.

```jsx
import { FocusTrap } from "focus-trap-react";

function Modal({ open, onClose, children }) {
  if (!open) return null;
  return (
    <FocusTrap focusTrapOptions={{ escapeDeactivates: true, onDeactivate: onClose }}>
      <div role="dialog" aria-modal="true">
        {children}
      </div>
    </FocusTrap>
  );
}
```

В этом коде focus автоматически переводится внутрь, ловится в trap, Escape закрывает модалку и возвращает focus на trigger (если ранее зафиксирована точка return). Семь строк кода, и поведение, которое руками воспроизводится в десятки раз дольше с десятком ошибок.

Нативный `<dialog>` с `dialog.showModal()` (а не `dialog.show()`) делает focus trap бесплатно, без библиотек. С учётом того, что кросс-браузерная поддержка `<dialog>` стабильна с 2022 года, для нового кода это часто лучший выбор: меньше зависимостей, корректное поведение из коробки, поддержка backdrop через CSS-псевдоэлемент `::backdrop`.

<MarginNote>
react-aria (Adobe Spectrum) — open-source с 2020 года, набор React-хуков для accessibility. Radix UI — open-source с 2020, в 2024 приобретён WorkOS. focus-trap (David Clark) — vanilla-библиотека, де-факто стандарт для focus trap в JS-проектах вне React-экосистемы.
</MarginNote>

<SectionBreak id="07" label="ПРОТОКОЛ ТЕСТИРОВАНИЯ" />

Тестирование с screen reader — навык, который тренируется. Зрячий разработчик, впервые включивший VoiceOver, обычно теряется в первые пять минут и закрывает его с ощущением «это невозможно использовать». Это нормальная реакция, и единственный способ её преодолеть — практика. Минимальный практический протокол, который стоит запускать перед каждым релизом:

**Шаг 1. Keyboard-only навигация.** Уберите мышь физически (отключите трекпад, мышь). Попробуйте выполнить ключевые сценарии: регистрация, основное действие продукта, оплата. Только Tab, Shift+Tab, Enter, Space, Escape, стрелки. Проверьте: достижимы ли все интерактивные элементы, виден ли focus всегда (включая моменты после закрытия модалок), нет ли keyboard traps (focus застрял внутри какого-то компонента и не выходит), возвращается ли focus на trigger после закрытия popup и модалок, работают ли skip links на длинных страницах. Это базовый уровень — без него остальное не имеет смысла.

**Шаг 2. Screen reader на основной flow.** Включите VoiceOver на Mac (Cmd+F5) или NVDA на Windows (Ctrl+Alt+N). Закройте глаза или отверните монитор — это важно: визуальный контекст обманывает мозг и заставляет «достроить» то, что SR не сказал. Пройдите ключевой сценарий, слушая голос. Что не озвучено? Где SR произносит «button» без имени? Где переходы между шагами не объявляются? Где после действия (submit, добавить в корзину) пользователь не получает подтверждения? Любой такой пробел — баг доступности, требующий фикса.

**Шаг 3. Проверка структуры через шорткаты.** В browse mode пройдите по странице шорткатами H (заголовки) и D (landmarks). Картина должна совпадать с визуальной структурой: h1 — название страницы, h2 — основные секции, h3 — подсекции; landmark — banner, navigation, main, contentinfo. Если шорткаты ничего не находят или находят бессмысленный список («h1, h1, h1, h3, h2, h4») — структура сломана, и любой пользователь с шорткатами потеряется.

**Шаг 4. Проверка форм и динамики.** Заполните форму, специально допуская ошибки. Озвучивает ли SR валидационные сообщения? Появляется ли подтверждение после submit? Если появляется toast — слышен ли он? Если редирект — объявляется ли новая страница (через изменение `<title>` и focus на h1)?

Рекомендованная WebAIM матрица тестирования — **один SR + один браузер на платформу**: NVDA + Firefox для Windows (исторически самая совместимая пара), VoiceOver + Safari для macOS и iOS (естественное сочетание). JAWS добавляется как контрольная точка перед major release или для enterprise-продуктов; покрывать все комбинации SR × браузер не нужно, эта работа дублирует сама себя.

Что важно понимать: автоматические инструменты (axe-core, Lighthouse, WAVE) screen reader не заменяют. Они проверяют наличие атрибутов и базовую корректность ARIA, но не отвечают на вопрос «осмысленно ли это звучит». Alt-текст «image123.jpg» формально присутствует, но бесполезен для пользователя — axe этого не поймает. Live region есть, но toast в нём появляется через `setTimeout` после полной перерисовки, и SR его не озвучивает — axe не воспроизведёт сценарий. Manual SR-тестирование — единственный способ это поймать, и оно остаётся в чеклисте релиза наравне с keyboard-only-проверкой.

<MarginNote>
WebAIM рекомендует тестировать с одним SR + одним браузером на платформу: NVDA + Firefox для Windows, VoiceOver + Safari для Mac/iOS. JAWS — как контрольная точка перед major release. Покрывать все комбинации не нужно: одна правильно построенная семантика работает во всех движках.
</MarginNote>

<SectionBreak id="08" label="СИНТЕЗ" />

Screen reader не озвучивает страницу — он переводит accessibility tree в речь. Эта tree собирается браузером из DOM с фильтрацией и обогащением; решения, принятые на её уровне, не отменяются ни визуальным дизайном, ни JavaScript-логикой. Семантический HTML — главный инструмент влияния на эту структуру: нативный `<button>` несёт роль, имя, фокус и keyboard-поведение бесплатно, ручная замена через `<div role="button">` повторяет всё это с почти гарантированными ошибками. Rule 1 of ARIA — «No ARIA is better than bad ARIA» — это инженерное наблюдение, не стилистический выбор.

Landmark-роли формируют структурный скелет, по которому пользователи SR навигируются шорткатами D и H, не последовательным чтением сверху вниз. Live regions решают задачу динамики: контент, появляющийся без изменения фокуса (toast, валидация, статус), должен быть в `<div role="status">` или `<div role="alert">`, существующем в DOM до появления текста. Focus management в модалках — отдельная дисциплина: focus trap внутри, возврат на trigger при закрытии, библиотечные решения вроде focus-trap, react-aria и Radix UI решают это правильно за разработчика. Протокол тестирования — keyboard-only, затем SR на основной flow, затем шорткаты H и D для проверки структуры; матрица NVDA + Firefox на Windows, VoiceOver + Safari на Mac.

Связь с двумя предыдущими темами трека прямая. WCAG 2.2 даёт нормативную рамку (POUR, success criteria, levels) — эта тема показывает, как часть этих критериев (4.1.2, 4.1.3, 1.3.1, 2.1.1, 2.4.3, 2.4.7) реализуются на уровне конкретной разметки и кода. Cognitive accessibility описывает невидимую сторону a11y — эта тема описывает другой край, тоже невидимый: продукт, который для зрячего разработчика «работает», для пользователя SR может оказаться полностью непригодным, и единственный способ это проверить — самому послушать.

Опишите: (1) какие изменения в семантике HTML и ARIA нужны, чтобы пользователь screen reader не пропустил toast и понял, что заказ оформлен; (2) как должен вести себя focus после submit — где он находится сразу после успеха, куда переходит после редиректа; (3) какие шорткаты SR использует на этой странице, чтобы понять структуру (h1, landmarks, поля формы), и как структура должна быть размечена, чтобы шорткаты работали; (4) как протестировать поток с VoiceOver или NVDA — конкретные шаги, которые должен сделать тестировщик.

  **Критерии оценки.** Хороший ответ упоминает: (1) toast реализован через постоянный `<div role="status" aria-live="polite" aria-atomic="true">` (или `role="alert"` для assertive, если контент критичен), существующий в DOM до появления сообщения; текст «Заказ оформлен» вставляется внутрь, а не вместе с контейнером; альтернативно — отдельная visually-hidden live region параллельно с visual toast; для редиректа после трёх секунд недостаточно: пользователь SR может не успеть услышать, лучше явно объявить переход или дать кнопку «Перейти к подтверждению» с focus на ней; (2) после успешного submit focus переводится либо на сам toast (если он interactive с `tabindex="-1"`), либо на главный заголовок страницы подтверждения после редиректа (focus на `<h1 tabindex="-1">`), либо на кнопку следующего шага; ни в коем случае не оставлять focus «висеть» на submit-кнопке или сбрасывать на body; (3) структура: `<header>` (banner), `<nav>` (если нужна), `<main>` со страницей формы, `<form>` с `aria-label` или `aria-labelledby` на h1; внутри формы — `<h1>` названия страницы, опционально `<h2>` группировки полей (контактные данные, адрес доставки, оплата); каждый input связан с `<label>` (не placeholder), required-поля помечены `aria-required="true"`, ошибки связаны через `aria-describedby`; landmark-навигация (D) находит banner, navigation, main; H находит h1 и h2-группы; F даёт быстрый переход между полями; (4) протокол тестирования: keyboard-only проход с Tab/Shift+Tab/Enter/Escape по всей форме без мыши, проверка focus visible на каждом шаге; затем NVDA или VoiceOver — пройти flow с закрытыми глазами, заполнить форму с намеренными ошибками (пропустить required-поле, ввести некорректный email), послушать валидационные сообщения, отправить форму, дождаться toast и редиректа, удостовериться, что каждый шаг озвучен; в browse mode пройтись по H и D, проверить, что структура читается; финальный шаг — повторить в Safari + VoiceOver на iPhone, потому что мобильная версия часто отличается от десктопной семантически.
</Exercise>
