<DropCap>К</DropCap>омпонентный API — это контракт между компонентом и его потребителем: какие props принимаются, какое поведение гарантируется, какие состояния допустимы. Контракт устаревает медленнее, чем визуал: визуальный refresh занимает недели, breaking change в API — месяцы рефакторинга всех мест, где компонент используется. Поэтому проектировать его стоит дороже, чем рисовать. Любой осмысленный API отвечает на четыре вопроса: что варьируется (variants), что заполняется (slots), куда монтируется (polymorphism), кто владеет состоянием (controlled vs uncontrolled). Эти четыре вопроса и составляют сетку, по которой стоит разбирать каждое решение в кнопке, поле, диалоге.

<SectionBreak id="01" label="ЧТО ТАКОЕ КОМПОНЕНТНЫЙ API" />

В предыдущей теме трека дизайн-токены были описаны как контракт между значением и компонентом: компонент читает имена, токены гарантируют, что у этих имён есть значения. Компонентный API — контракт уровнем выше: между компонентом и потребителем, который этот компонент использует. У него ровно та же природа — это именованный набор обязательств, и его изменения распространяются по системе так же, как изменения токенов, только дороже. Каждый сайт-потребитель — это место, где контракт зафиксирован в JSX-разметке, и каждое breaking change в API заставляет переписывать этот сайт.

Различие в стоимости фундаментально. Visual refresh — изменение токенов, которое может пройти без участия инженера потребляющего продукта: значения подменились, компоненты перерисовались, разметка не тронута. API breaking change — изменение, которое требует ручного вмешательства во всех местах, где компонент вызывается: переименование prop, удаление варианта, смена сигнатуры обработчика. В крупных продуктах кнопка используется тысячами вызовов; даже простое переименование `type` → `variant` — это месяц аккуратной миграции с deprecated-aliases и codemod'ами. Поэтому добавлять prop легко, удалять — почти невозможно. API растёт асимметрично: новые возможности приходят быстро, старые остаются годами.

На этом фоне четыре вопроса проектирования — не теоретическая схема, а способ удержать API от разбухания. Что варьируется — закрытый набор `variant`. Что заполняется — открытые точки `children` и slots. Куда монтируется — polymorphic API, `as` и `asChild`. Кто владеет состоянием — controlled vs uncontrolled. Каждый из четырёх вопросов имеет конечный набор приличных ответов; знание этих ответов экономит годы рефакторинга.

<SectionBreak id="02" label="VARIANTS — ЗАКРЫТЫЙ НАБОР" />

Variant — это закрытый перечислимый набор предустановленных оформлений. Кнопка в зрелой системе объявляет `variant: "primary" | "secondary" | "destructive" | "ghost" | "link"` — пять заранее одобренных образов поведения. Потребитель выбирает один из них; «своего» цвета или своей формы он не задаёт. Закрытость — главное свойство: variant не оставляет щели, в которую может протечь произвольное визуальное решение.

Почему не `color="#0066CC"`. Во-первых, такой prop ломает темизацию: значение цвета жёстко зашито в разметке потребителя и не реагирует ни на смену темы, ни на смену бренда. Семантический слой токенов, описанный в предыдущей теме, при таком API становится бесполезным — компонент перестаёт читать `color/action/primary`, потому что его перебили извне. Во-вторых, `color` ничего не говорит о роли: чёрная кнопка может быть и primary, и destructive, и ghost; цвет — это следствие роли, а не сама роль. В-третьих, открытый prop разрушает дизайн-консистентность: через полгода в продукте появится двенадцать оттенков «почти-primary», ни один из которых не пройдёт audit на доступность.

Те же правила работают для `size: "sm" | "md" | "lg"`. Размер — закрытое перечисление, ссылающееся на токены `space/inset/sm | md | lg` и `type/body/sm | md | lg`. Произвольный `paddingX={12}` — anti-pattern по тем же трём причинам.

В TypeScript variant выражается через discriminated union — это даёт type-safe сужение и автодополнение в IDE.

```tsx
type ButtonVariant = "primary" | "secondary" | "destructive" | "ghost" | "link";
type ButtonSize = "sm" | "md" | "lg";

type ButtonProps = {
  variant?: ButtonVariant;
  size?: ButtonSize;
  state?: "idle" | "loading" | "disabled";
  children: React.ReactNode;
} & React.ButtonHTMLAttributes<HTMLButtonElement>;
```

Главная архитектурная ловушка variants — combinatorial explosion. Если у компонента есть `variant` (5 значений), `size` (3), `disabled` (boolean), `loading` (boolean), то теоретическое пространство состояний — 5 × 3 × 2 × 2 = 60. Документировать, тестировать и поддерживать 60 ячеек — невозможно; команда быстро прекращает попытки и держит в голове «работающие» комбинации, остальные оставляет багами.

Решение — orthogonal props. Размер не зависит от варианта: любой variant работает на любом size. Состояние не зависит от размера: loading-кнопка остаётся той же кнопкой. Свойства, которые на самом деле взаимоисключающие (loading и disabled с точки зрения потребителя — почти одно), сворачиваются в одну prop с перечислением: `state: "idle" | "loading" | "disabled"`. Это убирает ситуацию, когда `loading={true}` и `disabled={false}` дают undefined-поведение, а `loading={true}` и `disabled={true}` — другое undefined-поведение. Конечный автомат с одной осью состояния всегда понятнее, чем матрица из независимых булей.

<MarginNote>
Polaris (polaris.shopify.com/components/actions/button), Material UI (mui.com/material-ui/react-button), Mantine (mantine.dev/core/button) — три каталога, в которых variant API кнопки оформлен наиболее аккуратно. Сравнение их сигнатур — полезное упражнение для понимания границ закрытого набора.
</MarginNote>

<SectionBreak id="03" label="SLOTS — ОТКРЫТЫЕ ТОЧКИ" />

Slots — это места в компоненте, в которые потребитель вставляет произвольный контент. Если variant закрывает «как выглядит», slot открывает «что внутри». Самый простой случай — единственный slot, который называется `children`: `<Card>{content}</Card>`. Карточка не знает, что лежит у неё внутри, и не должна знать; её работа — рамка, тень, скругление, отступ. Содержимое — ответственность вызывающего.

Когда мест больше одного, у дизайнера API возникает выбор. Первый путь — добавить named props: `headerContent`, `bodyContent`, `footerContent`, `actionsLeft`, `actionsRight`. Этот путь почти всегда плохой. Каждое новое место в карточке — новая prop с собственным именем, и через десять компонентов API превращается в свалку из тридцати слотов-через-props. Render props не композируются между собой: нельзя из `headerContent` дотянуться до `footerContent`, нельзя обернуть всё одним wrapper'ом. Anti-pattern индустрия называет «render prop взрыв».

Второй путь — compound components. Карточка экспортирует несколько связанных компонентов, и потребитель собирает её сам.

```tsx
<Card>
  <Card.Header>
    <Card.Title>Отчёт за квартал</Card.Title>
    <Card.Description>Январь — март 2026</Card.Description>
  </Card.Header>
  <Card.Body>{content}</Card.Body>
  <Card.Footer>
    <Button variant="ghost">Отмена</Button>
    <Button variant="primary">Сохранить</Button>
  </Card.Footer>
</Card>
```

У этой формы три преимущества. Композиция гибкая: можно опустить `Card.Footer`, переставить `Card.Header` под `Card.Body`, обернуть `Card.Body` в собственный layout. Имена самодокументирующие: разметка читается без обращения к docs. И — главное — общие настройки передаются через React Context: родительский `<Card variant="elevated">` объявляет вариант, дочерние `Card.Header` и `Card.Footer` читают его через `useContext(CardContext)` и подстраиваются. Это даёт связность без передачи props через все уровни.

Эта же модель лежит в основе headless-библиотек. Radix Primitives собирает Tabs из `<Tabs.Root>`, `<Tabs.List>`, `<Tabs.Trigger>`, `<Tabs.Content>`; Dialog — из `<Dialog.Root>`, `<Dialog.Trigger>`, `<Dialog.Portal>`, `<Dialog.Overlay>`, `<Dialog.Content>`. Каждый подкомпонент — отдельная единица, и связь между ними держится через контекст. Базовая идея совпадает с тем, что делает Base UI (MUI); Headless UI Tailwind Labs смешивает compound с render-props; React Aria идёт другим путём — это набор поведенческих хуков (`useButton`, `useDialog`), а не готовых compound-блоков.

Slot-API имеет свою ловушку — слишком много обязательных слотов. Если карточка требует от потребителя обязательно заполнить `Card.Header`, `Card.Title`, `Card.Description`, `Card.Body`, `Card.Footer` — это плохой контракт: каждое использование превращается в шесть строк boilerplate. Решение — давать default-content или делать слоты опциональными, оставляя только `children` обязательным. Хороший compound API — тот, в котором простое использование занимает строку, а сложное — десять.

<MarginNote>
Radix Primitives (radix-ui.com/primitives) — каноничная реализация compound components в React; читать стоит исходники Tabs и Dialog. Sebastian Markbåge из React core team в публичных обсуждениях 2017–2019 годов аргументировал, почему контекст и compound API превосходят render props для большинства композиционных задач.
</MarginNote>

<SectionBreak id="04" label="POLYMORPHIC — `as` И `asChild`" />

Polymorphic API решает проблему, которая возникает у любой стилизованной кнопки: семантически она иногда `<button>`, иногда `<a href>`, иногда `<NextLink>`, иногда `<Link>` из React Router. Визуально — одно и то же; HTML-элемент — разный. Если оставить только `<Button>`, потребитель не сможет сделать ссылку, выглядящую как кнопка, без обхода API.

Решение первое — prop `as`. Stitches, Mantine, ChakraUI пошли этим путём.

```tsx
<Button as="a" href="/dashboard">К дашборду</Button>
<Button as={NextLink} href="/settings">Настройки</Button>
```

`as` принимает строку (имя HTML-тега) или компонент. Внутри Button рендерится переданный элемент с накладыванием стилей и поведения кнопки. Подход рабочий, но имеет два технических неудобства. Тип `as` сложно правильно вывести: TypeScript должен сузить набор допустимых props в зависимости от значения `as` (для `as="a"` появляется `href`, для `as="button"` — `type`), и это требует тяжёлой generic-машинерии в типах. Runtime-проверка тоже не идеальна: нельзя гарантировать, что переданный компонент примет все props, которые Button захочет ему передать.

Решение второе — `asChild`, представленное Radix Primitives и популяризированное shadcn/ui.

```tsx
<Button asChild>
  <a href="/dashboard">К дашборду</a>
</Button>

<Button asChild>
  <NextLink href="/settings">Настройки</NextLink>
</Button>
```

Логика обратная. Button не рендерит собственный `<button>`; он берёт ровно того ребёнка, которого ему передали, и накладывает на него свои props и поведение. Type-safe, потому что ребёнок — реальный JSX-элемент, который TypeScript уже проверил отдельно. Технически реализуется через утилиту `@radix-ui/react-slot`: компонент `<Slot>` клонирует единственного ребёнка и мержит свои props с его props, разрешая конфликты по понятным правилам (event-handlers вызываются оба, className конкатенируется, style мержится).

```tsx
import { Slot } from "@radix-ui/react-slot";

const Button = React.forwardRef<HTMLButtonElement, ButtonProps>(
  ({ asChild, className, ...props }, ref) => {
    const Comp = asChild ? Slot : "button";
    return <Comp ref={ref} className={cn(buttonStyles, className)} {...props} />;
  }
);
```

shadcn/ui построен на этом паттерне — `asChild` встречается во многих компонентах библиотеки, и большинство интеграций с роутерами Next.js, React Router, Remix решаются именно через него.

Между двумя подходами стоит выбирать осознанно. `as` удобнее для очень мелких компонентов (typography-примитивы, в которых нужно менять `<h1>` на `<h2>` без потери стиля); `asChild` стабильнее для интерактивных компонентов, где важна корректная передача поведения. Современные системы в основном выбирают `asChild`.

<SectionBreak id="05" label="CONTROLLED VS UNCONTROLLED" />

Четвёртый вопрос API — кто владеет состоянием. У любого компонента, у которого есть внутреннее состояние (открыт/закрыт у диалога, выбранная вкладка у tabs, значение у инпута), есть два возможных режима. Uncontrolled — состояние живёт внутри компонента, потребитель не знает о нём напрямую. Controlled — состояние живёт снаружи, потребитель передаёт текущее значение и колбэк изменения.

Браузерный `<input>` — каноничный пример. `<input defaultValue="hello">` — uncontrolled: браузер хранит value, потребитель только читает финальное значение. `<input value={x} onChange={(e) => setX(e.target.value)}>` — controlled: state живёт в потребителе, инпут только отображает.

Каждый режим хорош в своих случаях. Uncontrolled — проще: меньше кода, меньше re-render'ов, не нужен useState на каждое поле. Применяется, когда потребителю не нужно знать промежуточное значение — например, в форме, у которой важен только submit. Controlled — гибче: можно валидировать на каждое нажатие клавиши, можно изменять значение программно, можно синхронизировать с другим состоянием. Применяется, когда состояние компонента влияет на остальной интерфейс.

Хороший API не выбирает за потребителя — он поддерживает оба режима. Pattern «controlled с поддержкой uncontrolled» выглядит так:

```tsx
type SwitchProps = {
  checked?: boolean;          // controlled
  defaultChecked?: boolean;   // uncontrolled
  onCheckedChange?: (checked: boolean) => void;
};

function Switch({ checked, defaultChecked, onCheckedChange }: SwitchProps) {
  const [internalChecked, setInternalChecked] = React.useState(
    defaultChecked ?? false
  );
  const isControlled = checked !== undefined;
  const value = isControlled ? checked : internalChecked;

  const handleChange = (next: boolean) => {
    if (!isControlled) setInternalChecked(next);
    onCheckedChange?.(next);
  };

  return <button role="switch" aria-checked={value} onClick={() => handleChange(!value)} />;
}
```

Контракт здесь простой. Если потребитель передал `checked` — компонент в controlled-режиме, внутреннее состояние не используется, всё значение приходит извне. Если `checked` не передан — компонент в uncontrolled-режиме, использует `defaultChecked` как начальное значение и хранит state внутри. `onCheckedChange` вызывается в обоих случаях, потому что потребителю иногда нужен callback даже при uncontrolled (например, чтобы закрыть меню после выбора). Если переданы оба — `checked` и `defaultChecked` — это ошибка использования; зрелые библиотеки выводят dev-warning.

Radix Primitives в этом дисциплинирован образцово. Tabs, Dialog, Popover, Accordion — все поддерживают оба режима: `value` / `defaultValue` для tabs, `open` / `defaultOpen` для модалок. Это позволяет начать с uncontrolled (быстро, мало кода), а затем перейти на controlled (когда понадобилась внешняя синхронизация) — без переписывания компонента, только изменением вызова.

<MarginNote>
Reactовая документация описывает controlled/uncontrolled в разделе про forms (react.dev/reference/react-dom/components/input). Radix-овская трактовка распространена шире — почти каждый компонент в radix-ui.com/primitives документирует оба варианта.
</MarginNote>

<SectionBreak id="06" label="ЧАСТЫЕ ОШИБКИ" />

Несколько типичных промахов API повторяются в большинстве систем, и каждый из них стоит дороже исправления, чем профилактики.

**Boolean props взрыв.** У компонента появляется `isLoading`, потом `isError`, потом `isSuccess`, потом `isWarning`. Каждое — отдельный boolean, и в JSX можно передать любую комбинацию: `isLoading && isError`, `isSuccess && isWarning`. Что должно отрисоваться — undefined: автор компонента не предусмотрел такой случай, и поведение зависит от порядка проверок в реализации. Проблема — в API: семантически это одна ось состояния, выраженная как несколько независимых булей. Решение — единое перечисление: `state: "idle" | "loading" | "error" | "success" | "warning"`. Конечный автомат с одной осью гарантирует, что в каждый момент компонент находится ровно в одном состоянии, и эти состояния документируются списком, а не таблицей.

**Magic strings без TypeScript.** Если variant — обычная строка `string`, опечатка `variant="primry"` пройдёт компиляцию и упадёт в проде как невидимая ошибка: компонент получит неизвестный variant, проигнорирует его и отрисуется как default. TypeScript-ный union (`"primary" | "secondary" | ...`) ловит это в момент написания кода: IDE подсветит ошибку, codemod при переименовании variant не пропустит ни одного места. Любая закрытая ось должна быть union'ом, не строкой. То же касается размеров, состояний, ориентаций — всего, что перечислимо.

**Прокидывание `className` без понимания.** Кнопка принимает `className` и подставляет его в корневой элемент. Потребитель пишет `<Button className="bg-red-500">` — и переопределяет системный фон. Контракт нарушен: variant сказал «primary» (синий), className сказал «red», итог — красный. Спорить с этим бессмысленно: потребитель победит. Решение — `cn()`-утилита: комбинация `clsx` для условного слияния классов и `tailwind-merge` для разрешения конфликтов Tailwind-классов. `tailwind-merge` знает, что `bg-red-500` и `bg-blue-500` принадлежат одной утилитарной группе, и оставляет тот, который передан последним в порядке merge — обычно это className потребителя; не возникает каскада с непредсказуемым порядком. shadcn/ui распространил эту утилиту по индустрии — `cn(buttonStyles, className)` стало нормой.

**Слишком много обязательных слотов.** Если compound-карточка требует от потребителя заполнить все шесть подкомпонентов, простое использование становится длиннее, чем сама задача. Хороший API стремится к тому, чтобы общий случай занимал одну строку, специальный — десять. Это проверяется на реальных использованиях: если на 80% сайтов вызова повторяется один и тот же boilerplate — boilerplate должен стать default'ом, а не остаться требованием.

**Прокидывание стилей через props вместо variants.** `<Button paddingX={12} borderRadius={8} background="#0066CC">` — API, который выглядит гибким, на деле уничтожает дизайн-систему: потребитель собирает кнопку «как нужно», игнорируя любую systemic дисциплину. Гибкость должна быть закрыта в variants и slots; всё, что не покрывается ими — повод для разговора с дизайнером, а не для нового prop.

Четыре вопроса — variants, slots, polymorphism, controlled vs uncontrolled — вместе составляют сетку, по которой стоит проектировать любой компонент дизайн-системы. Variants отвечают за закрытое разнообразие оформлений; slots — за открытое заполнение содержимым; polymorphism через `as` или `asChild` — за смену семантического носителя без потери визуала; controlled/uncontrolled — за владение состоянием. Каждый из четырёх вопросов имеет ограниченное число приличных ответов, и зрелые системы в индустрии — Radix, shadcn/ui, Polaris, Material UI, Mantine — расходятся в деталях, но не в принципах.

Связь с двумя предыдущими темами трека прямая. Дизайн-токены — то, на что ссылается реализация компонента изнутри: variant `primary` определяется через `color/action/primary` и `space/inset/md`, не через хардкод значений. Без semantic-слоя токенов variant перестаёт работать как абстракция: он становится привязан к конкретному цвету, и вся система рассыпается. Atomic Design — то, что задаёт convention каталога, в котором этот компонент живёт: button — atom, card — organism, dialog — pattern. Сам по себе атом ничего не говорит про API; API проектируется отдельно.

Компонентный API — стык трёх слоёв системы. Снизу — токены, на которые он ссылается. Сверху — каталог, в котором он лежит. В центре — контракт, который он предлагает потребителю. Если этот контракт продуман — токены работают, каталог растёт без хаоса, потребители не пишут обходных путей. Если не продуман — никакая дисциплина токенов и никакая аккуратность каталога не спасает: продукт всё равно будет полон `<Button style={{ background: "#0066CC" }}>` и `<div className="card">`, написанных в обход системы.

Следующая тема трека — governance: как API дизайн-системы поддерживается в долгом времени. Кто принимает решение о добавлении нового variant; кто инициирует deprecation старого; как организуется миграция с breaking change; что фиксируется в RFC-процессе. Сегодняшний разговор о контракте — про то, как он устроен в моменте; следующий — про то, как он живёт между моментами.
