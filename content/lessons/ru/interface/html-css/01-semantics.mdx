<DropCap>Х</DropCap>ороший HTML-документ читается дважды: браузером, который рисует пиксели, и всем, что пикселей не рисует — screen reader'ом, поисковым ботом, парсером RSS, разработчиком через полгода. Div-вёрстка работает только в первом чтении; на втором — молчит. Семантика — не вопрос «правильно vs неправильно», а вопрос количества смысла на единицу кода: тэг, выбранный точно, заменяет три ARIA-атрибута, четыре event listener'а и пояснительный комментарий. Эта тема — про то, как разметка несёт значение и почему отказ от семантики обходится дороже, чем кажется на этапе вёрстки.

<SectionBreak id="01" label="ЗАЧЕМ СЕМАНТИКА — ЧЕТЫРЕ АУДИТОРИИ" />

HTML отдаётся одновременно четырём аудиториям, и у каждой свои ожидания от разметки. Семантика — общий протокол, через который эти ожидания выполняются без дополнительных усилий со стороны автора.

**Браузер.** У каждого тэга — user-agent stylesheet и встроенное поведение. `<h1>` рендерится крупным; `<button>` получает фокус по Tab, активируется по Space и Enter; `<form>` отправляется по Enter; `<input type="email">` на мобильном открывает клавиатуру с символом @. Это не «магия» — контракт спецификации HTML. Заменив `<button>` на `<div>`, автор отказывается от всего пакета и должен реализовать его руками, обычно неполностью.

**Ассистивные технологии.** Screen reader'ы — NVDA (NV Access, бесплатный), JAWS (Freedom Scientific), VoiceOver (встроен в macOS и iOS) — обращаются к странице через accessibility tree, который браузер строит на основе семантики. Для AT `<button>Подписаться</button>` — «кнопка, Подписаться»; `<div onclick>Подписаться</div>` — просто «Подписаться», без указания на интерактивность. Без семантики интерфейс для незрячего пользователя — плоский список текстовых фрагментов.

**Поисковые системы.** `<h1>` — заголовок документа, влияющий на ранжирование; `<article>` — самостоятельная единица контента; `<nav>` — навигация, исключаемая из основного индекса; structured data в `<script type="application/ld+json">` — машиночитаемое описание. Семантика — часть on-page SEO, более устойчивая, чем мета-теги, и более дешёвая, чем link building.

**Будущие разработчики.** Включая автора через полгода. `<nav>` понятнее, чем `<div className="nav">`; `<main>` указывает на главное; `<aside>` объясняет, почему блок может быть скрыт на мобильном. Семантика — документация, встроенная в код. Цена — выбор тэга, ноль дополнительных строк.

<MarginNote>
WHATWG HTML Living Standard (html.spec.whatwg.org) — текущая спецификация HTML, обновляемая непрерывно с 2004 года. Пришла на смену зафиксированным версиям W3C HTML 4.01 / 5.0 / 5.1 / 5.2 и сегодня является нормативным источником.
</MarginNote>

Одну из четырёх аудиторий можно проигнорировать без катастрофы. Все четыре сразу — нет: продукт, не работающий ни для AT, ни для SEO, ни для будущей команды, копит долг, который проявляется через год в виде «надо переписать с нуля».

<SectionBreak id="02" label="DOCUMENT OUTLINE" />

Скелет страницы строится из небольшого набора структурных тэгов, появившихся в HTML5 (2014) и доведённых до универсальной поддержки к середине 2010-х.

```html
<body>
  <header>
    <nav>...</nav>
  </header>
  <main>
    <article>
      <h1>Заголовок страницы</h1>
      <section>
        <h2>Раздел</h2>
        ...
      </section>
      <section>
        <h2>Другой раздел</h2>
        ...
      </section>
    </article>
    <aside>...</aside>
  </main>
  <footer>...</footer>
</body>
```

`<main>` — главное содержимое, ровно один раз на документ. Всё, что внутри, — то, ради чего пользователь пришёл; всё снаружи — обрамление. Screen reader-команда «перейти к основному содержимому» работает через этот landmark.

`<article>` — самостоятельная единица контента, имеющая смысл вне страницы: пост в блоге, карточка товара, комментарий, новостная заметка. Тест — можно ли вырезать и опубликовать отдельно, не потеряв смысл. Если да — `<article>`; если нет — `<section>` или `<div>`.

`<section>` — тематический раздел внутри документа, обычно с собственным заголовком. `<section>` без `<h1>`-`<h6>` бессмысленна; если у блока нет заголовка, нужен `<div>`. Частая ошибка — заменить все `<div>` на `<section>` и сломать outline безымянными пунктами в дереве заголовков.

`<aside>` — побочное содержимое, связанное с основным, но не критичное для понимания: sidebar, callout, related-content, реклама. AT часто читают его после основного или предлагают пропустить.

`<header>` и `<footer>` — контекстные тэги. На уровне `<body>` это шапка и подвал страницы; внутри `<article>` — шапка поста (заголовок, метаданные) и подвал поста (теги, дата, author bio). Переиспользование тэга — намеренная конструкция: «header» относителен к ближайшему sectioning element.

`<nav>` обозначает группу навигационных ссылок. Не каждый список ссылок — `<nav>`: WHATWG рекомендует использовать его для основной навигации и крупных блоков (table of contents), но не для каждой группы из трёх ссылок в подвале.

<MarginNote>
MDN HTML Element Reference (developer.mozilla.org/docs/Web/HTML/Element) — каноническое практическое руководство по тэгам с примерами, замечаниями о доступности и таблицами поддержки браузерами. Поддерживается Mozilla с 2005 года.
</MarginNote>

<SectionBreak id="03" label="HEADINGS КАК OUTLINE" />

Тэги `<h1>` — `<h6>` создают древовидную структуру документа, по которой screen reader-пользователь перемещается едва ли не чаще, чем по landmark'ам. По WebAIM Screen Reader User Survey 2024, около 70% респондентов ставят headings первым или вторым способом навигации. Иерархия заголовков — не декоративная задача, а функция навигации.

**Одна `<h1>` на страницу.** Это название документа, аналог title-page книги. На главной — название продукта; на странице статьи — заголовок статьи. Wordmark в шапке не должен быть `<h1>`, если страница не посвящена бренду как таковому: для этого есть `<img alt>` или `<div>`. Две и более `<h1>` — устаревший паттерн, оставшийся от обсуждавшегося в HTML5 «document outline algorithm», который ни один браузер не реализовал. Действующая рекомендация WHATWG — одна `<h1>`, дальше последовательная иерархия.

**Не пропускать уровни.** После `<h2>` идёт `<h3>`, не `<h4>`. Пропуск — нарушение outline: screen reader произнесёт «heading level 4» там, где ждали «level 3», и навигация по дереву теряет предсказуемость. Accessibility tree берёт уровень из тэга буквально.

**Visual size ≠ heading level.** `<h2>` можно сделать мельче `<h3>`, если того требует визуальный ритм — это вопрос CSS, не разметки. Уровень заголовка определяет логическую иерархию, размер шрифта — визуальную; оси независимы. Решение — отделить размерный класс от семантики: `<h3 class="text-sm-bold">` валидно и иерархию не нарушает.

**Skip link.** На длинных страницах первый интерактивный элемент часто — невидимая ссылка `<a href="#main-content">Перейти к основному содержимому</a>`, появляющаяся при фокусе. Screen reader- и keyboard-пользователь обходит повторяющуюся навигацию одним Tab + Enter.

<SectionBreak id="04" label="LANDMARKS" />

Landmarks — крупные навигационные ориентиры, через которые AT-пользователь прыгает по структуре, не прослушивая всё подряд. В NVDA клавиша **D** открывает список landmark'ов; в VoiceOver — **VO+U** (Control+Option+U) с табом «Landmarks». Без landmark'ов AT-пользователь скроллит руками или слушает страницу линейно.

Большинство HTML5-тэгов имеют ARIA-роль по умолчанию: `<main>` ≡ `role="main"`, `<nav>` ≡ `role="navigation"`, `<aside>` ≡ `role="complementary"`, `<header>` верхнего уровня ≡ `role="banner"`, `<footer>` верхнего уровня ≡ `role="contentinfo"`. Дублировать роль не нужно — `<nav role="navigation">` избыточно и в части линтеров триггерит предупреждение.

ARIA-атрибуты применяются там, где у HTML нет встроенного эквивалента: состояние аккордеона (`aria-expanded`), связь input'а с описанием (`aria-describedby`), подпись иконочной кнопки (`aria-label`), live-регион для динамических уведомлений (`aria-live`). Это инструмент — но он не подменяет семантику, уже встроенную в HTML.

Несколько landmark'ов одного типа различаются через `aria-labelledby` или `aria-label`: две `<nav>` — основная и в подвале — должны быть подписаны, иначе screen reader прочтёт обе как «navigation» без различения.

```html
<nav aria-label="Основная навигация">...</nav>
<nav aria-label="Навигация в подвале">...</nav>
```

<MarginNote>
*ARIA Authoring Practices Guide* (W3C, w3.org/WAI/ARIA/apg) — официальный сборник паттернов взаимодействия от Web Accessibility Initiative с примерами кода для autocomplete, dialog, tabs, treeview и других составных компонентов.
</MarginNote>

<SectionBreak id="05" label="INTERACTIVE ELEMENTS" />

Самая частая ошибка семантики — интерактивные элементы через `<div>` или `<span>` с `onclick`. Цена — каскад потерь, каждую из которых приходится восстанавливать руками.

```html
<!-- Плохо -->
<div class="btn" onclick="submit()">Отправить</div>

<!-- Хорошо -->
<button type="submit">Отправить</button>
```

`<button>` бесплатно даёт: фокус по Tab, активацию по Space и Enter, focus indicator из user-agent stylesheet, объявление AT как «кнопка», участие в Forms list, корректное поведение в составе `<form>`, состояние `:disabled`. Эквивалент на `<div>` требует `role="button"`, `tabindex="0"`, обработчики `keydown` для Space и Enter (с `preventDefault` от скролла на Space), управление `aria-disabled`, ручная стилизация focus. Половина деталей пропускается — и кнопка ломается тихо, без visible bug.

**`<a href>` против `<button>`.** Anchor — переход на URL (смена страницы, якорь). Button — действие на текущей странице (открыть модалку, переключить состояние). Конвертация ломает поведение: `<button>` с `history.push()` визуально как ссылка, но не открывается в новой вкладке по middle-click и Cmd+click, не показывает URL, не копируется через «Copy Link». Обратное — `<a href="#" onclick>` — ломает навигацию назад и индексацию.

```html
<a href="/products/42">Карточка товара</a>
<button type="button" onclick="openModal()">Подробнее</button>
```

**Form elements** — `<input>`, `<textarea>`, `<select>`, `<label>`, `<fieldset>`, `<legend>`. Каждый input связан с `<label>` — обёрткой или через `for` / `id`. Без label screen reader объявит «edit text» без указания назначения. Placeholder — не замена: исчезает на фокусе, теряет контраст и не читается AT как имя поля.

```html
<label for="email">Email</label>
<input id="email" type="email" name="email" autocomplete="email" required>
```

`type="email"` открывает на мобильном клавиатуру с @; `autocomplete="email"` позволяет менеджеру паролей подставить значение; `required` включает встроенную валидацию. Три атрибута — три бесплатных слоя UX, которые часто реализуют через JavaScript заново.

**`<dialog>`** — тэг, впервые реализованный в Chrome ещё в 2014 году и получивший повсеместную поддержку только к 2022-му (Firefox 98 и Safari 15.4 — обе в марте 2022). Лучшая альтернатива div-модалкам: `showModal()` управляет focus trap, ESC закрывает диалог по умолчанию, `::backdrop` стилизуется через CSS, возвращение фокуса на trigger встроено. До `<dialog>` модалка — 200-строчный custom hook; с `<dialog>` — 5 строк HTML и пара строк JavaScript.

```html
<dialog id="confirm">
  <form method="dialog">
    <p>Удалить элемент?</p>
    <button value="cancel">Отмена</button>
    <button value="confirm">Удалить</button>
  </form>
</dialog>
```

<MarginNote>
Heydon Pickering, *Inclusive Components*, Smashing Magazine, 2017 — практический справочник по построению доступных компонентов (toggle, modal, menu, tab, autocomplete) на минимальной семантике HTML с минимумом ARIA. Главный тезис — «каждый раз, когда выбираете ARIA, спросите, нет ли HTML-эквивалента».
</MarginNote>

<SectionBreak id="06" label="ARIA AS LAST RESORT" />

W3C *ARIA Authoring Practices* открывается формулой, известной как «First Rule of ARIA»: «If you can use a native HTML element with the semantics and behavior you require already built in, then do so». Это инженерное правило, выведенное из десятилетнего опыта ошибок W3C и индустрии.

ARIA — слой обещаний, не подкреплённых поведением. `<button>` обещает кнопку и является ею — фокус, клавиатура, состояния в комплекте. `<div role="button">` обещает кнопку, но не является — обещание держит автор разметки, и каждый незакрытый зазор оборачивается багом доступности.

Допустимое использование ARIA:

- `aria-label` на иконочной кнопке без текста (`<button aria-label="Закрыть"><svg>...</svg></button>`)
- `aria-expanded="true|false"` на триггере раскрытия (accordion, dropdown)
- `aria-describedby` для связи input'а с подсказкой или сообщением об ошибке
- `aria-live="polite"` на регионе с динамическими уведомлениями (toast'ы)
- `aria-current="page"` на ссылке текущей страницы
- `role="alert"` или `role="status"` для регионов, требующих немедленного объявления

Анти-паттерн — `<div role="button" tabindex="0" onclick aria-pressed="true">`. Каждый атрибут компенсирует то, что `<button>` даёт по умолчанию. Один забыт — результат хуже, чем `<button>`, и сложнее в отладке.

**Conflict.** `<button role="link">` создаёт когнитивный диссонанс у AT: кнопка по поведению (Space активирует), ссылка по объявлению (screen reader скажет «link»). Не переопределяйте роль семантического тэга, кроме задокументированных случаев (например, `<ul role="tablist">` в ARIA APG).

**Плохой ARIA хуже, чем без ARIA.** Без атрибутов AT знает, что не знает. С неверным ARIA AT получает ложную уверенность: `<input aria-label="Email">` на поле телефона прозвучит как «Email», и пользователь введёт email не туда.

<MarginNote>
Heydon Pickering, *Inclusive Design Patterns*, Smashing Magazine, 2016 — отдельная книга, тематически продолжающая *Inclusive Components* (2017): как строить доступные интерфейсы на семантике HTML с минимумом ARIA.
</MarginNote>

<SectionBreak id="07" label="ИНСТРУМЕНТЫ И ПРОВЕРКА" />

Семантика проверяется тремя способами — автоматическим, визуальным и поведенческим.

**Автомат.** Lighthouse в Chrome DevTools — Accessibility audit на axe-core. axe DevTools (Deque) — отдельное расширение с более подробными правилами. `eslint-plugin-jsx-a11y` ловит часть проблем на этапе линтинга: `<div onClick>` без role, missing alt, label без for, `<a>` без href. HTML-валидатор W3C — для синтаксиса.

**Визуально.** Browser DevTools → Accessibility tree показывает, как страница выглядит для AT: роли, состояния, имена. `<div>` объявлен как «button» без accessible name — проблема; `<button>` с иконкой объявлен пустым — нужен `aria-label` или текст.

**Поведенчески.** Уберите мышь, пройдите ключевой flow на Tab. Включите VoiceOver (Cmd+F5) или NVDA, пройдите его со звуком. 10-15 минут на критический путь — ловит то, что автотесты не ловят: отсутствие skip link, неудобный порядок фокуса, неинформативные accessible names, missing live regions.

Тема [accessibility/wcag-practical](/lessons/ru/experience/accessibility/01-wcag-practical) разбирает principles и levels; этот урок — материал, на котором эти принципы реализуются.

<SectionBreak id="08" label="СИНТЕЗ" />

Семантика — контракт между автором разметки и тремя машинами (браузером, AT, поисковиком) плюс одним человеком (следующим разработчиком). Контракт несимметричный: автор тратит секунды на выбор тэга, машины и человек получают пакет поведения и понимания. Дёшево для пишущего, дорого для пропускающего — главный аргумент в пользу семантики.

Семантический HTML не даёт всего, что нужно для доступного интерфейса — focus order, контраст, error messages, keyboard traps лежат за пределами выбора тэга. Но даёт фундамент, без которого остальное бесполезно: ARIA на div'ах не починит отсутствие document outline; контрастный focus ring не заменит того, что фокус не приходит на элемент.

Следующая тема — `02-box-model`. Если семантика отвечает на «что это», box model — на «как это занимает место»: width, height, padding, border, margin, и почему `box-sizing: border-box` стал индустриальным дефолтом к середине 2010-х. Без него дизайнер не предсказывает, как ляжет в макет правильно подобранный элемент, — и разговор о Flexbox, Grid и container queries в следующих темах окажется построен на проверенном фундаменте.
